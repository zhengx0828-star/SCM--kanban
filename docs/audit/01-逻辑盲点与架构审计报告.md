## 1. 🔴 致命级问题（会白屏 / 会给出错误业务结论）

### F-01 · 脏 JSON 导致库存信号塔整页 500

- **位置**：`backend/app/routers/inventory.py:128-141` `_parse_month_qty()`
- **代码**：
  ```python
  try:
      data = json.loads(raw)     # 只兜住了「解析失败」
  except (TypeError, ValueError):
      return []
  out = []
  for item in data:              # ← 第 137 行：data 若是 123 / 1.5 / true，这里抛 TypeError
  ```
  内层 `except (TypeError, KeyError, ValueError)` 只包住 `out.append(...)`，**不包 `for` 本身**。
- **实测证据**（探针 P2）：

  | hist_json 原始值 | 期望 | 实测 |
  |---|---|---|
  | `123` | 200 忽略 | **500** |
  | `1.5` | 200 忽略 | **500** |
  | `true` | 200 忽略 | **500** |
  | `{"m":"2026-09","q":1}` | 200 忽略 | 200（dict 迭代取 key，被内层 except 兜住） |
  | `"abc"` / `abc` | 200 忽略 | 200 |
- **影响**：任一行数据被写坏（历史脚本 / 手工改库 / 未来 import 路径变更），`GET /api/inventory/plans` 直接 500，**整个库存信号塔白屏，且前端无法定位是哪一行**。
- **修复**：`json.loads` 后加 `if not isinstance(data, list): return []`（1 行）。

### F-03 · 需求恒 0 时静默显示「正常」——最危险的静默失败

- **位置**：`_resolve_demand()`（`inventory.py:319-347`，`scaled = q × bom_factor`）+ `InventoryPage.tsx:762` 的 `noDemandData = hist.length === 0 && fcast.length === 0`
- **实测证据**（数据集 `SSD222 / TEST-ZERO-030 / TS-C01 / 青岛`）：
  - 底表 `PSR.demand = [2000×12]`，`bom_factor = 0`
  - 接口返回：`avg_daily=0, ss=0, rop=0, replenish=null, status=blue(过剩)`，且 `hist/fcast` 是 12 个 `0` → **非空** → 琥珀「缺需求数据」徽章**不显示**
  - 前端渲染结果：**「正常 / 30 天内无需补货」**
- **定性**：这不是"没数据"，而是"有数据但被算成 0 且无任何提示"。用户看到的是**绿色的健康结论**，而真实情况是每月有 2000 件需求没有进入推算。
- **同类**：`bom_factor = NULL` 被静默当成 `1.0`（数据集 `DVSF132/TEST-BIG-040/TS-E01`），口径同样未声明。
- **修复**：新增 `no_demand` 语义（`avg_daily == 0` 或需求序列全 0 → 琥珀徽章「需求为 0，请确认 BOM 与客户需求」+ 建议条「无法推算补货建议」）；`bom_factor == 0` 单独给红字提示。

### F-05 · 批量建档批内重复 → 整批 500，已选记录全部丢失

- **位置**：`inventory.py:880-892` `bulk_create_plans()`
- **代码**：`_ensure_selectable()` 在循环内被 `try/except HTTPException` 包住 → 只覆盖「维度不存在」；**同一四元组重复不在校验范围内**，冲突延迟到循环外的 `db.commit()` → `IntegrityError` 未被捕获。
- **文档承诺**：函数 docstring 写着「逐条校验并创建；**单条失败不影响其余**，错误按行号回传」。
- **实测证据**（探针 P1）：`{"items":[{A},{A}]}` → **HTTP 500 `Internal Server Error`**，且 `created` 也不会是 1（整批事务回滚）；重复调用仍 500（非幂等）。
- **影响**：前端「批量选取底表组合建档」只要用户勾选出现重复（底表本身允许同项目同物料多供应商，很容易重复勾选），**整批失败且无任何中文原因**。
- **修复**：`_ensure_selectable` 内增加 `ExistingPlan` 检查（返回 409 中文原因），循环后改逐条 `flush()` + 捕获 `IntegrityError`；批内先按四元组去重。

### F-10 · 删除仍被库存档案引用的供应商 → 库存页整页 500

- **位置**：`suppliers.py` 删除端点（只做 `db.delete()`）+ `inventory.py:_build_plan_out()` 中 `plan.supplier.name`
- **实测证据**（探针 P5）：
  ```
  DELETE /api/suppliers/{id} → 204
  随后 GET /api/inventory/plans → 500
  ```
  原因：`InventoryPlan.supplier` 变为 `None`，输出层直接取 `.name` 抛 `AttributeError`。
- **根因**：① 删除前未校验 `inventory_plans` 引用（对比：删 `base_sites` 有 409 保护，**供应商/物料没有**）；② SQLite **`PRAGMA foreign_keys` 未开启**，`ondelete="CASCADE"`（`models.py:331-334`）形同虚设，不会被数据库兜住。
- **修复**：删除前查引用 → 409 + 中文原因（"该供应商仍被 N 条库存档案引用，请先删除档案"）；输出层加 `plan.supplier.name if plan.supplier else "—"` 兜底；`database.py` 开启 `PRAGMA foreign_keys=ON`。

### F-11 · 删除项目不清理下游表 → 孤儿行 + rowid 复用污染新项目

- **位置**：`projects.py:186-190` `delete_project()` + `models.py:196-198`
- **代码**：`Project` **只声明了 `supply_links` 一条 `cascade`**；`ShareRecord` / `InventoryPlan` 与 `Project` 之间**没有 relationship**，ORM 不会级联；SQLite 外键又未启用 → 两张表全部残留。
- **实测证据**（探针 P4）：
  ```
  残留 share_records=1、project_supply_relations=0、inventory_plans=1
  ```
- **连带危害（本次实测意外复现，比残留本身更严重）**：SQLite 的 `rowid` 会被**复用**。孤儿 `inventory_plans` 的 `project_id` 被"新建项目"重新占用后：
  ```
  POST /api/inventory/plans → 409
  {"detail":"档案已存在：TMP-PRJ-b324657bb9 · TMP-PN-b324657bb9 · 临时探针供应商b324657bb9 · 青岛"}
  ```
  报错里出现的**全是新数据自己的名字**，但命中却是那条孤儿行 —— 排查时几乎不可能想到根因。同理，新项目还会**静默继承**孤儿 `share_records`，被 `UNIQUE(project_id, supply_relation_id, month)` 挡住或直接污染 dashboard 统计。
- **修复**：`delete_project()` 内显式按 `project_id` 删除 `inventory_days` → `inventory_plans` → `share_records` → `project_supply_relations`；或统一开启外键并补齐 relationship。

## 2. 🟠 高风险问题

### F-02 · 月份键不归一化 + 30 天窗口跨年时需求静默归 0

- **位置**：`_parse_month_qty()`（`out.sort(key=lambda x: x.m)` 按**字符串**排序）、`_resolve_demand(plan, psr, year)` 的 `year` 实参来自 `base.year`、`fcast_map.get(_month_key(d))`
- **实测证据**（探针 P3）：
  - `hist_json = [{"m":"2026-7"},{"m":"2026-8"},{"m":"2026-9"}]` → 接口**原样返回 `['2026-7','2026-8','2026-9']`**，不补零、不归一化；`sort` 会把 `'2026-7'` 排在 `'2026-09'` 之后。
  - `fcast_json` 含 `2027-01`：当前窗口（10 月）不触发；但 `_month_array_to_items(psr.demand, year=2026)` 与 `_month_key(d)=f"{d.year}-{d.month:02d}"` 的组合意味着——**12 月窗口里 1 月的 30 天会去 2026 年的 map 里查 2027-01，取到 0**。
- **影响**：每年 12 月，看板对"跨年 1 月"的需求全部按 0 计算 → 期末库存虚高 → **系统性漏报次年 1 月的断货**。同时底表 `capacity` 按 `order_day.month` 取值（`inventory.py:487`），1 月下单会取到**当年 1 月**的额度（F-09 同源）。
- **修复**：统一 `YYYY-MM` 归一化（`f"{y}-{m:02d}"`）；`_resolve_demand` 改为传 `base: date` 并构造 `{(year, month): q}` 的映射；capacity 同理按 `(year, month)` 对齐。

### F-06 · `on_hand` 缺 `ge=0`，可写负库存

- **位置**：`schemas.py:776` `InventoryPlanUpdate.on_hand: float | None = None`
- **对照**：同文件 `795` `InventoryPlanCreate.on_hand: float = Field(0, ge=0)` **有**约束；`lead_time_days` 也有 `gt=0`（故探针里 `lead_time_days=0/-5` 正确返回 422）。
- **实测证据**（探针 P6）：`PATCH {"on_hand": -100}` → 200；`{"on_hand": -1e9}` → 200。
- **影响**：一旦写入负库存，该行**当天即判「已断货」**（`ending <= 0`），且 30 天矩阵出现极端负数，图表 Y 轴被拉爆。
- **修复**：`on_hand: float | None = Field(None, ge=0)`。

### F-08 · 产能额度显式录入 0 被判为 `na`（与「未录额度」混淆）

- **位置**：`inventory.py:489`
  ```python
  if capacity_limit is not None and capacity_limit > 0:
      ... ok / tight / short
  else:
      capacity_status = INV_CAPACITY_NA
  ```
- **实测证据**（探针 P7）：`PATCH capacity=[0]*12` → `capacity_limit=0.0, capacity_status=na`，前端显示「**未录额度** —— 请到供需管理补录」。
- **影响**：`0` 与 `NULL` 是**两个完全不同的业务含义**——`0` = "本月没给这家供应商分额度"（严重缺口，任何补货都超额度 → 应判 `short`），`NULL` = "还没录"。当前把前者伪装成后者，**把红色缺口显示成灰色待办**。
- **修复**：`capacity_limit is not None` → `limit == 0` 时 `capacity_usage = inf` 并判 `short`；仅 `None` 才 `na`。

### F-15 · dashboard-stats 用 `max(month)`，脏月份会整片遮住当期风险

- **现象（种子脚本收尾时真实踩到）**：负向测试往 `share_records` 写了 `2026-13` / `2026-00` / `2026-12` / `2027-01` 后，`GET /api/share/dashboard-stats` 的 `month` 跳到那个空月份 → **首页风险数据整片变空**；必须在 `finalize()` 里删掉这些行才恢复（见 `scenario_manifest.json → finalize.deleted_share_rows = 5`）。
- **根因**：默认统计月 = 表内 `max(month)`，而不是「当前自然月」或「最近一个**有数据**的月份」。
- **影响**：任何一次误写/预填未来月份的份额，都会让首页风险总览**无声无息地归零**——用户不会知道是数据问题。
- **修复**：默认月优先取「当前自然月」，无记录再回退「≤ 当前月的最大月份」；同时给 `month` 加格式校验（`01-12`）。

### F-04 · master 模式把全年 12 个月（含未来）当作「历史」算 COV

- **位置**：`_resolve_demand()` 结尾
  ```python
  return scaled, scaled, INV_SOURCE_MASTER, psr.bom_factor
  #      ↑ 同一份序列既当 hist（算 COV 的样本）又当 fcast（未来预测）
  ```
- **对比**：snapshot 模式下 `hist_json` 是 Excel 提供的**历史**、`fcast_json` 是**未来**，两者分离。
- **影响**：两种模式的 COV 口径不一致；master 模式下 COV 实际是"**计划波动**"而非历史波动，且未来月份波动会污染安全库存；未录月份被当 0 参与均值（拉低均值、抬高 COV）。
- **修复**：master 模式下 `hist` 只取 `m < 当月` 的月份（不足 2 个月自然走兜底）；若坚持现行口径，则必须把字段/文案从"历史波动 COV"改成"计划波动"并在规则页写明。

### F-18 · 份额「小数 / 百分数」判定是**记录级**的，混合写法静默错 100 倍

- **规则回顾**：`share` 若全 ≤1 视为小数（×100）；否则按百分数解读。该判定在**一整条记录的所有基地行**上做，而不是逐行。
- **实测证据**（数据集 `RB-SC-12`，`2026-09`）：
  ```
  bases = [{base:"常州", lines:1, share:0.5}, {base:"苏州", lines:1, share:50.0}]
  → share_current = 25.25
  ```
  因为苏州写了 `50.0`（>1），整条记录被判为"百分数口径"，于是常州的 `0.5` 被读成 **0.5%** 而不是 50%。加权 = (0.5×1 + 50×1)/2 = **25.25%**；若按用户显然的意图（0.5 与 50 都表示 50%），应为 **50%**。
- **影响**：同一条记录里，一个基地用小数写、另一个基地用百分数写 —— 这是**极其自然的录入习惯** —— 结果自动份额与由此派生的「建议配额」「风险归类」全部偏离一倍以上，而且**没有任何提示**。
- **修复**（任选其一，建议前两条同时做）：
  1. 判定改为**逐行**：单行 `0 < share ≤ 1` → ×100；前端在输入框上明确单位（`%` 后缀），提交前统一归一化。
  2. 当同一记录内**同时出现**"≤1 的值"与">1 的值"时，返回 422 并提示"份额口径混用，请统一为 0-100 的百分数"。
  3. 至少在 `share_records` 上落一个 `share_unit`（percent/decimal）字段，把隐式启发式变成显式契约。

### 设计确认（不是 bug，但需前端更醒目）

- **`RB-SC-10`**：`bases=[{常州, lines:2, share:80}, {重庆, lines:2, share:null}]` → 自动份额 40%。重庆这条 **share 为空但 lines 有值**，仍进入分母（`Σlines=4`），把常州从 80% 摊薄到 40%。**这正是既定规则**（"share 空 = 不供但拉线仍入分母"），数据与口径一致；但 UI 上"空 share"和"0 share"视觉相同、后果却不同，建议对空 share 基地行加一条脚注/图标说明"该基地未分配份额，但已计入分母"。

### F-19 · 份额月份格式校验漏掉 `01-12` 范围

- **位置**：`share.py` 的月份 `pattern`（形如 `^\d{4}-\d{2}$`）
- **实测证据**（`scenario_manifest.json → rollover_and_negative` 第 3、4 条）：
  ```
  POST /api/share/records {"month":"2026-13"} → 201     ← 通过
  POST /api/share/records {"month":"2026-00"} → 201     ← 通过
  ```
- **连带危害**：这两条非法月份直接触发了 **F-15**（dashboard-stats 取 `max(month)` → `2026-13` 最大 → 首页风险总览整片归零）。种子脚本不得不在收尾里删掉 5 条此类脏行才能让看板恢复可用。
- **修复**：pattern 改为 `^\d{4}-(0[1-9]|1[0-2])$`；并在 rollover / dashboard-stats 入口做一次防御性过滤。

### F-20 · 份额记录可写到「该项目未挂载的供应关系」上

- **实测证据**（同上第 7 条）：
  ```
  往「未挂载该供应关系」的项目写份额 → 201 写入成功
  ```
- **影响**：份额记录脱离了 `project_supply_relations` 这个"项目 × 供应关系"的挂载事实 → 该条记录会出现在份额页排行/四象限里，但对应的项目明细页看不到它；`dashboard-stats` 的 `by_project` 计数也会虚高。属于**数据孤岛 + 统计污染**。
- **修复**：写份额前校验 `ProjectSupplyRelation(project_id, supply_relation_id)` 存在，否则 409 + 中文原因（"该项目未挂载该供应关系，请先在供需管理中挂载"）。

### F-21 · `rollover` 未校验 `to_month ≥ from_month`，反向结转被静默跳过

- **实测证据**（同上第 2 条）：`to_month` 早于 `from_month` → **200，无任何提示**，但实际一条都没结转。
- **影响**：用户点错月份后看到"成功"，以为已结转，实际数据没动。
- **修复**：`to_month < from_month` → 422「结转目标月份必须晚于来源月份」。

## 5. 架构层盲点（非 bug，但需要决策）

1. **SQLite 外键全局失效**：`models.py` 里大量 `ondelete="CASCADE"` 是**装饰性**的——`PRAGMA foreign_keys` 默认关闭。所有删除级联目前完全依赖 ORM relationship（F-10/F-11 的根因）。这是一个**全局性架构决定**，建议要么开启 PRAGMA、要么把 `ondelete` 全部删掉以免误导后来者。
2. **`supply_relations.capacity` 无录入入口**：库存页"产能校验"分母用的是该项目分到的月额度（`PSR.capacity`），而 `capacity_used` 参考值取的 L2 供应商总产能**没有任何 UI 可以录入**——该字段永远为 `null`。属功能性缺口。
3. **`/api/inventory/summary` 遗留接口未接 UI**（docstring 已标注）。
4. **跨年时间轴**：整个库存模块用「today 年 + 月份下标」表达时间（F-02/F-09），在 12 月会集体失准。这是一次性的架构选择，但**每年 12 月都会复发**，建议在真正跨年前修掉。
5. **`demand` / `capacity` 用定长 12 数组**：隐含"只有当年、只有 12 个月"的假设，无法表达跨年度需求，也没有月份维度的年份信息。
