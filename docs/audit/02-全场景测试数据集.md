## 5. 维度三 · 级联风险传导（Cascading Impact）

数据集中刻意用**同一个核心物料** `TEST-CORE-001` 串起三个项目：

```
TS-A01（核心件独供主路径）
   └─ TEST-CORE-001
        ├─ SSD222  → 宁波 / 常州 / 苏州 / 重庆   （4 个基地）
        ├─ DVSF132 → 重庆                        （IN-S011：断供传导）
        └─ SOCK124 → 东莞                        （IN-S012：断供传导）
```

- 同一个 `TEST-CORE-001` 在三个项目里各有独立的库存档案与份额记录 → 验证**上游（供应商）一次波动，下游多基地/多项目同时亮灯**时，各行是否会互相污染计数。
- `IN-S003`（DOH 6.8 < LT 30）与 `IN-S008`（LT 60）覆盖**已不可逆**（今天下单也来不及）这一类最高危形态，对应顶部卡①的「其中 N 行下单也来不及」提示。
- 份额侧 `RB-SC-02/03/07` 覆盖"上游份额变化 → 下游风险标签"的传导。

## 7. 如何使用

### 重建整个数据集（幂等，会先清空）
```bash
cd D:/scm-kanban
runtime/python/python.exe scripts/seed_test_scenarios.py
```
前置：后端已在 `http://127.0.0.1:8000` 运行。脚本会打印全量核对表并以 `快照行一致性：15/15` 结尾；同时刷新 `scenario_manifest.json` 与 `inventory_snapshot_import.xlsx`。

```bash
runtime/python/python.exe scripts/_probe_and_cleanup.py
```

输出 → `docs/audit/probe_results.json`。脚本只使用 `TMP-*` 临时实体，**结束即回收**（并会兜底清全库孤儿行）。

```bash

```

## 8. 已知覆盖缺口（诚实声明）

1. **并发写入**：未构造并发场景（如两人同时改同一天日格、同时跑 rollover）。
2. **大数据量**：最大行为 21 个推算单元 × 30 天。未构造 500+ 行 / 12 个月完整需求矩阵的性能场景。
3. **多年度**：数据全部落在 2026 年。**跨年窗口（today 在 12 月）没有静态数据覆盖**——F-02 是通过直接改库 + 推理确认的，不是数据集触发的。
4. **供应商产能 `capacity_used`**：该字段取自 L2 `supply_relations.capacity`，但系统**没有任何 UI 可录入**，故数据集里也全为 `null`（属功能缺口，非覆盖缺口）。
5. **前端交互细节**：下拉/抽屉/浮层的交互态用无头 Chrome 的 DOM 快照验证（无 NaN、无白屏），未做逐控件点击回归。
6. **`inventory_days` 只覆盖单字段**：未测试「同一天同时给 demand_override + manual_demand + manual_in + ending_override 四个字段」的组合叠加顺序。
