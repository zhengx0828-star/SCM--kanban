## 4. 需求可用性的三档递进（F-03 的完整形态）

修复过程中发现「有序列但为 0」与「完全没有序列」在 UI 上是两回事，最终落成**三档互斥**，按「谁最具体」排序：

| 档位 | 触发条件 | 徽章 | 建议条 | 业务含义 |
|---|---|---|---|---|
| **缺需求数据** | `hist.length = 0 && fcast.length = 0` | 琥珀 | 「缺需求数据，无法推算补货建议」+ 引导去供需管理补录 | 从来没录过（含底表 `PSR.demand` 为空） |
| **BOM 为 0** | 底表联动且 `bom_factor` 显式为 0 | **红** | 「BOM 系数为 0，需求被乘为 0」+ 引导修正 BOM | 有客户需求，被 BOM 乘成了 0 |
| **需求为 0** | 有序列且窗口日均需求 ≈ 0 | 琥珀 | 「需求为 0，无法推算补货建议」+ 提示确认是否漏录 | 有数据但那 12 个月都是 0 |

> 这里修掉了一个**嵌套缺陷**：后端 `has_series` 最初写成 `bool(hist or fcast) or source == MASTER`，把「底表联动但 `PSR.demand` 为空」也算成"有序列"，于是 `TEST-SOLE-010` 被错标成「需求为 0」而不是「缺需求数据」。改成只看实际序列，前端再补一层 `&& !noDemandData` 防御。
>
> 关键设计取向：**这三档都压过颜色语义**。没有数据的行不该因为 `ROP=0 → 永不跌破` 而显示绿色「正常」——那是最危险的一种"看起来没问题"。

## 6. 遗留与后续建议

1. **`supply_relations.capacity`（L2 供应商总产能）仍无录入 UI** —— 库存页行尾的 `capacity_used` 参考值目前恒为空，形同虚设。两条路：在「供应商管理」补录入入口，或把该字段从库存页移除以免误导。属产品决策，本次未动。
2. **静态枚举扫描探针（P8）是新增的回归门禁** —— 后端若新增 `status` / `cov_label` / `capacity_status` / `risk_type` 取值，先跑它能立刻发现前端漏兜底。
3. **迁移机制**：`backend/app/migrations.py` 幂等执行，`main.py` lifespan 里 `create_all` 之后调用。改「约束 / 删列」类结构变更须走「建新表 → 拷数据 → DROP → RENAME」，且必须在 `PRAGMA foreign_keys=OFF` 下做，否则 `DROP inventory_plans` 会连带把 `inventory_days` 级联清空。
4. **规则页「待定」项**：集团侧「各项目额度合计 > 总产能」的超分预警尚未实现（已在规则页显式标注为待定，不做默认值）。
