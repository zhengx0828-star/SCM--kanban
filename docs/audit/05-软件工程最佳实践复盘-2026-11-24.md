# 软件工程最佳实践复盘 · SCM Kanban

日期：2026-11-24
范围：`backend/app`、`frontend/src`、`scripts`、根目录构建与交付脚本、版本控制状态、文档一致性。
方法：5 个独立审查视角（数据层 / 安全 / 前端 / 测试交付 / 架构）分别实读代码取证，结论经交叉核对；对冲突结论做了二次验证（见附录）。

## 一、结论先行

这个项目的**业务建模水平明显高于工程配套水平**。需求版本化 + 投影、份额四层校验、细分打分纯函数化、Pydantic 错误中文化，这些设计放在内部系统里属于上游水准。真正拖后腿的不是"代码写得糙"，而是三件事：

1. **没有机器化的"改完必须过"关卡**，所以验证只能靠人打开页面看，于是回归靠肉眼、提交靠勇气。
2. **事务边界不设防**，"双写"和"批量导入"这类必须原子完成的操作被拆成多次提交，异常时会留下半截数据，而下游读投影的设计会把半截数据放大成业务结论错误。
3. **同一套业务口径没有单一真相源**，供需三档写三遍、阈值存两份、常量前后端各一份，靠注释里的"必须一致"维系。

按严重度：**P0 8 条、P1 12 组、P2 10 条**。P0 里 7 条是"现在就在发生"，1 条是"一次意外就无法挽回"。

## 二、P0：会造成错误结论、数据不可逆丢失，或已经断了退路

### P0-1　71 个文件没提交，GitHub 上那份代码是 22 天前的

**证据**
```
git log -1        → 5b162df 2026-11-02 17:38
git status        → 43 modified + 28 untracked
```
未跟踪文件里包含**核心模块**：`backend/app/supplier_risk.py`（被 `projects.py:60`、`suppliers.py:19` import）、`frontend/src/components/projects/ManageMaterialsDialog.tsx`（被 `ProjectSupplyDetailPage.tsx:20` import）、`docs/supplier-risk/`。

**通俗解释**

**修法**
先给 `.gitignore` 补 `backend/probe_*.py`、`backend/init_*.py`、`.env`（否则 `git add -A` 会把带口令的排障脚本推上 GitHub），再按主题分 4-5 次提交。

### P0-2　需求"版本表 + 投影"分两次提交，中途失败即永久不一致

**证据**　`backend/app/routers/projects.py:238` 与 `:252`
```python
db.commit()          # 238：版本行 + is_current 已落库
db.refresh(ver)
if ver.is_current:
    _write_demand_projection(db, project_id, demand_json)   # 内部再 db.commit()
```

**通俗解释**
先记账本、再抄到墙上。抄到一半断电，账本是 V2、墙上还是 V1。而后端所有下游都读墙上的数（`alerts.py:226` 读 `ProjectSupplyRelation.demand`，`inventory.py:422` 按 BOM 折算也读它）。结果是版本下拉显示 V2，供需预警和库存推算仍按 V1 算——两个页面互相打架，且**再没有任何写入会修复它**。

**修法**
`_demand_version_create` 与 `_write_demand_projection` 内部全部去掉 `commit()`，只 `flush()`；由调用方在投影写完后统一提交一次。改动约 5 行。

### P0-3　三条 API 旁路能绕过版本表直接改投影

**证据**　`projects.py:670-674`（PATCH 项目明细）、`projects.py:575-578`（新建明细）、`projects.py:650-653`（快速挂载）
```python
if "demand" in data:
    data["demand"] = _list_to_json(data["demand"])   # 直接改投影，不产生版本
```
`schemas.py:415` 仍然放行 `demand` 字段。

**通俗解释**
版本表是"唯一真相源"，但后门开着。任何人 `PATCH /api/projects/{id}/relations/{link_id}` 带个 `demand`，就能改数不记账：版本历史里查不到，供需页已经变了。前端现在只用它写 `capacity`，但脚本、Excel 导入的下一版、未来任何一个新功能一踩就中。

**修法**
从 `ProjectSupplyRelationCreate/Update`、`QuickCreate` 里删掉 `demand`；三处 `if "demand" in data` 分支一并删除。需求只允许走 `PUT /projects/{id}/demand` 或 `/demand-versions`。

### P0-4　变更 Excel 导入"边写边校验"，有错也提交

**证据**　`changes.py:1112` 文档写"先校验、后写入"，实际 `:1230` 解析阶段就 `db.add(...); db.flush()`，`:1387-1392` 无任何错误门禁直接 `db.commit()`。对比 `share.py:1541` 有 `if result.errors: raise 422`。

**通俗解释**
导入 10 张单，第 7 张的父任务找不到 → 记一条错误、跳过、继续跑完、返回 200。前 6 张已入库，用户看到的是"成功 + 一条提示"。更严重的是：缺任务的单子因为叶子全完成，`_refresh_change_summary` 会把状态刷成"已完成"——**一张任务不全的变更单被系统判定为已完成**，这不是显示问题，是业务结论错了。

**修法**
解析阶段只收集 `parsed_changes` / `parsed_tasks`，不落库；全部解析完 `if result.errors: db.rollback(); raise 422`；再进写入阶段，最后单次 commit。

### P0-5　删项目会静默级联删掉供应商细分评价与红黄牌

**证据**　`projects.py:375` → `_purge_orphan_master_data` → `:438` 删物料、`:454` 删供应商，检查项只有 `SupplyRelation` / `InventoryPlan` / `Change`，**没有检查 `SupplierSegment` / `SupplierCard`**。而 `models.py:619-620` 是 `ondelete="CASCADE"`。

**通俗解释**
某供应商只服务被删的那个项目（单项目供应商很常见）→ 删项目后它成了孤儿 → 被清理函数删掉 → 它的 12 项打分、历史快照、红黄牌一起 CASCADE 消失。接口只返回 204，没有任何提示。而这套数据的设计前提明确写着"档位原值不覆盖、解牌后可恢复"，被一个删除动作无声抹掉，且不可恢复。

**修法**
`_purge_orphan_master_data` 在 `db.delete(material)` / `db.delete(supplier)` 前各加一次 `SupplierSegment` / `SupplierCard` 计数检查，有引用就跳过；`materials.py:118` 的删除接口同样补 `SupplierSegment` 检查。

### P0-6　接口挂了，看板显示 0，不显示错

**证据**　`DashboardPage.tsx:123-135` 全部解构默认 `= []`，且无 `isError`；全站 11 个页面只有 `ProductsPage.tsx:45` 有 `isError`。`main.tsx` 与 `App.tsx` 均无 `ErrorBoundary`（全仓 `componentDidCatch` 零命中）。

**通俗解释**
后端 500 或超时，老板打开 Dashboard 看到的是"项目 0、物料 0、独供 0、库存<3 天 0、地图空白"——一组看起来完全正常的数字。**一块永远显示 0 的看板比一块报错的看板危险得多**，因为它会被当成真实结论使用。
另外任一页面渲染异常（如 `toDate(node.done_at)!` 空值）会整页白屏，没有返回路径。

**修法**
顶层加 `ErrorBoundary`；`DashboardPage` 等页面补 `isError` 分支（复用已有 `EmptyState` + 重试）；或在 `QueryClient` 的 `QueryCache.onError` 里统一 toast。

### P0-7　没有任何自动回归闸门

**证据**　全项目唯一测试文件 `backend/scripts/smoke_test.py`，18 条 `check()` 全部只覆盖 `/api/products` 的 CRUD。真正懂业务的断言在 12 个手工脚本里：`verify_share_import.py`（59 条）、`verify_segments.py`（40 条）、`verify_alerts.py`（六类预警 + 排序），没有任何 CI 或 pre-commit 会跑它们。`ruff.toml` / `pyproject.toml` / `.eslintrc` / `.pre-commit-config.yaml` / `.github` 全部不存在。

**通俗解释**
改完 `scoring.py` 或 `share.py`，唯一验证方式是打开页面看数字对不对。这直接解释了 P0-1——为什么 22 天不敢提交：提交了也不知道坏没坏。这些断言本身质量很高（"六项全 0.5 → 50 分不算过关"这种边界都写了），只是**没人跑**。

**修法**
它们已经是 `check(name, cond)` 结构，套一个 pytest fixture 就能收编。先做 `backend/tests/test_invariants.py`，收最贵的三组；再挂 `.pre-commit`（ruff + pytest）。

## 四、架构债：同一套口径没有单一真相源

这一节单独展开，因为它是"每次微调都是一次抽奖"的根源。

**1. 单文件巨型化，改一处要读两千行**

| 文件 | 行数 | 实际职责 |
|---|---|---|
| `routers/changes.py` | 2084 | 类型字典 CRUD / 变更单 CRUD / 任务树 / 状态派生 / 汇总 / 总览 / 预警 / 燃尽 / Excel 导入 300 行 / 导出 / 归档 |
| `routers/share.py` | 1679 | 份额计算 / QDC 校验 / 风险归类 / 预警 / KPI / 四象限 / **810 行单函数导入（内含 16 个闭包）** / 结转 |
| `routers/inventory.py` | 1656 | 30 天推算 / DOH / 补货建议 / 产能校验 / 分桶 / 批量建档 / 导入 / 导出 |
| `schemas.py` | 1747 | **115 个 class** + QDC / 权重 / 预警阈值 / 库存阈值全套业务常量 |
| `pages/ChangesPage.tsx` | 1548 | 1 个页面组件 + 30 个 hook，取数、甘特、燃尽、三饼图、预警表、看板、表单全在一个函数里 |

**2. 业务常量住在 DTO 文件里**
`schemas.py:543 QDC_SCORES`、`:546 WEIGHT_SCHEMES`、`:811 INV_CAPACITY_TIGHT_RATIO`、`:1444 ALERT_SEVERITY_ORDER`。想改"份额波动 ±30%"这种纯业务阈值，得去 1747 行的接口定义文件里翻。而 `scoring.py` 已经证明正确做法（常量收敛 + 纯函数 + 40 条断言），share/inventory 却在反方向走。

**3. 阈值两份，靠注释维系**
`schemas.py:1447` 原文："★ 与前端 `lib/supply-risk.ts` 的 `TIGHT_RATIO_MIN / TIGHT_RATIO_MAX` 必须一致"。这是一条"人类纪律"，不是"机器约束"。同理 `types/segment.ts:4 SEGMENT_TIERS` vs `scoring.py:21 TIERS`，且 a6 维度名已经漂移（"供应商质量服务分" vs "质量服务分"）——**说明这套机制已经在失效**。

**4. 反向依赖**
`alerts.py` 从三个 router 里 import 私有函数，`supplier_risk.py` 再从 alerts import 一层。依赖方向是 router ← 聚合层，与正常分层相反。给 `changes.py` 顶部加一行 import 就可能成环；`_task_state` 改名要跨 4 个文件。

**5. 可测试性**
93 个需要 DB Session 的 router 函数里，纯函数只有 `scoring.py` 的 6 个。`share.py` 里最关键的 ±1% 校验写在 endpoint 体内，想写断言必须先起服务 + 造库。

## 五、P2：该修，不紧急

1. `supply_relations.capacity` 与 `project_supply_relations.capacity` 同名不同层，注释互相矛盾（`models.py:181` vs `:258`），迟早出现"同一供应商在不同项目产能不一样"。
2. `PUT /api/share/records/{id}` 实际是部分更新，且 `if payload.x is not None` 导致字段永远无法清空（`share.py:760-771`）。
3. 批量建档 `items` 只有 `min_length=1` 没有上限（`schemas.py:1028`）；Excel 上传 `await request.body()` 无体积上限、无魔数校验。
4. 四个导入接口的 `file_path` 参数可读服务器任意本地 xlsx（`inventory.py:1276`、`changes.py:1128`、`share.py:877`、`segments.py:558`），应删除该分支。
5. 无 `TrustedHostMiddleware`，localhost 服务可被 DNS rebinding 绕过 CORS 白名单；`/docs`、`/openapi.json` 未关闭。

## 附录：被证伪的一条结论

审查过程中有一条高优先级指控需要澄清：`backend/requirements.txt:5` 的 `httpx2>=0.28` 曾被怀疑是仿冒包（typosquatting）。

**核实结果：不是。** PyPI 上 `httpx2` 2.16.2（2026-11-16 发布）由 Pydantic 官方接管维护，是 HTTPX 的延续包；`starlette==1.8.0` 的依赖说明明确写 "Test client built on `httpx2`"，`TestClient` 依赖的正是它。所以这一行**写法正确**，不必修改。

真正成立的相关问题只剩两条：`uvicorn` / `openpyxl` 等无上界、后端无 lock 文件（见 P1-14）。
