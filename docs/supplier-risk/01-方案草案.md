# 供应商红黄绿 判定方案（草案）

地图点位现在的颜色来自 `suppliers.risk_level`，**库里 6 家全是 NULL**——也就是全靠人工打标，没有规则。
本方案给出自动判定口径，不改动任何现有阈值，全部复用各模块已有函数。

---

## 1. 先划边界：什么数据能算到「一家供应商」头上

| 数据 | 归属层级 | 能否精确归到供应商 | 用途 |
|---|---|---|---|
| 库存推算单元 `inventory_plans` | 项目 × 物料 × 供应商 × 基地 | **能**（`supplier_id` 必填） | 断货 / 低于安全线 |
| 份额台账 `share_records` | 项目 × 物料 × 供应商 × 月 | **能**（经 `supply_relation`） | 独供（波动/偏差/错配暂不纳入） |
| 红黄牌 `supplier_cards` | 供应商 | **能**（供应商级） | 质量事故 |
| 供需缺口 `supply_relations.capacity` | 项目 × 物料（产能为该项目所有供应商合计） | **不能** | 物料级预警，**不进供应商颜色** |
| 变更单 `changes` | 项目 × 任务 | **不能**（无供应商字段） | 不进颜色 |
| 细分评分 `cap_score / will_score` | 月 × 物料 × 供应商 | 能，但它是「合作质量」不是「风险事件」 | 只通过红黄牌与错配间接参与 |

结论：**颜色只由前四类决定**。供需缺口若强行按供应商着色，同物料 3 家会一起变红，地图失去区分度——留给 P2 的可选口径（见 §7）。

---

## 2. 四档定义

一句话版本（2026-11-03 用户定稿）：

- **红：凡影响交付的。** 红黄牌、断货、库存跌破、供需缺口、人工标红。
- **黄：不影响交付的。** 有进行中的变更、唯一货源（独供，但当前有货）。
- **绿：以上都不命中。** 含没有份额/库存台账的供应商。
- **灰：** 接口未返回时前端兜底，正常不出现。

### 2.1 红（命中任一）

| 编号 | 规则 | 判定来源 | 阈值 |
|---|---|---|---|
| R1 | 红牌或黄牌生效（红黄牌都算红） | `supplier_cards`，复用 `segments._active_card_today` | `effective_from ≤ 今日 ≤ effective_to`（含空） |
| R2 | 已断货 | `inventory._status_of` → `INV_STATUS_STOCKOUT` | 期末库存 ≤ 0 |
| R3 | 库存跌破安全线 | `inventory._status_of` → `INV_STATUS_RED` | 期末 < SS 或 DOH < 安全天数（未到 0） |
| R4 | 供需缺口 | `alerts._supply_items` → `kind="shortage"` | 产能 ÷ 需求 < 1.0（1.0~1.3 的「偏紧」不算） |
| R5 | 人工标红 | `suppliers.risk_level = red` | 只允许加红，不能把自动红刷绿 |

R3 不再要求「独供」：库存跌破本身就影响交付，不管有几家供应。

### 2.2 黄（命中任一）

| 编号 | 规则 | 判定来源 | 阈值 |
|---|---|---|---|
| Y1 | 有进行中的变更 | `changes`：`status=active` 且未归档、未作废 | 变更在途，未必影响交付（2026-11-03 从红降黄） |
| Y2 | 唯一货源 | `share_records.is_sole = 1`，且该供应商**没有**库存跌破/断货 | 交付没问题，但没备份 |

库存已跌破或断货的，走 R2/R3 判红，不再重复记一条黄理由。
变更单 `supplier_id` 有值只算那一家，为空则按物料推断（表单目前没有供应商字段，实际都走推断）。

### 2.3 绿 / 灰

- **绿**：以上都不命中。至少有一个可判信号也好，一个都没有也好，都是绿（用户口径）。
- **灰**：接口未返回判定结果时的兜底，正常不会出现。

## 3. 供应商级聚合

一家供应商会同时挂在多个项目 × 物料上，颜色取**最严重的那个格子**，不取平均、不取多数。

```
level = red  if 任一红规则命中
      = yellow if 任一黄规则命中
      = green  if 有可判信号且无命中
      = none   otherwise
```

理由：A 项目断供、B 项目正常，地图上不能显示绿色。地图回答的是「这家能不能指望」，不是「平均下来还行」。

`reasons` 全量保留（页面只显示前 3 条 + 「另 N 条」），每条都带数字，例如：
- 「已断货：2 个推算单元（项目 P-001）」
- 「独供：3 个物料，其中 2 个有需求」
- 「份额波动：上期 40% → 本月 20%（-20pt）」

同色内排序（用于预警清单，地图不排序）：
- 红：断货单元数 ↓ → 独供物料数 ↓ → 红牌
- 黄：独供物料数 ↓ → 库存红档单元数 ↓ → 波动幅度 ↓

---

## 4. 刻意不做的四件事

1. **不用供需缺口给供应商上色。** 产能是项目内多家合计，缺口是物料级结论，归因到单家会把无辜供应商染红。要看缺口的去供需页，那里有物料级热力图。
2. **不用变更单。** `changes` 没有供应商维度，硬接只能按项目推断，等于编。
3. **不把评分低等同风险高。** 能力 40 分的供应商可能供货很稳，只是配合度差；反过来 90 分的独供一样会断货。评分只通过红黄牌和份额错配参与。
4. **不用供应关系条数。** 挂的物料多不等于风险大。
5. **份额波动 / 建议偏差 / 份额×评分错配暂不纳入。** 用户要的是「影响交付就红、不影响就绿」的简单口径，这三条属于「该调整但没坏」，现阶段不进颜色；将来要加，走黄色（不影响交付的结构性风险）。

## 5. 与预警中心的关系

`alerts.py` 第 6 类来源 `source="supplier"` 一直留着没接。本方案落地后按同样方式接入：

- 一条供应商预警 = 一个红/黄供应商，`severity` 映射：红 → P0（已造成影响：断货），黄 → P1（条件不健康）；
- 绿不产生预警；
- 灰是否进「数据缺口」列待定（灰的成因是台账缺失，属于人没录，不是供应商风险）。

接入前先做 P0（地图上色），不要两件事一起动。

## 6. 实现落点

新增 `backend/app/supplier_risk.py`，纯函数、无 ORM 副作用：

```python
def assess(db, supplier_ids: list[int] | None = None) -> dict[int, SupplierRisk]:
    """返回 {supplier_id: {level, reasons[], stats{stockout_units, red_units, sole_materials, ...}}}"""
```

- 判定函数全部 import，不复制：`inventory._status_of`、`share._is_fluctuation`、`share._is_mismatch`、`segments._active_card_today`。
- `GET /api/suppliers` 增加 `risk: {level, reasons, stats}` 字段，**实时计算、不落库**——与 alerts 一致：源数据修好了，颜色立刻变，不存在「台账已补、地图还红着」。
- 前端 `types/supplier.ts` 加 `risk` 字段；`ChinaMap` 着色改读 `risk.level`，tooltip 增加第一条 reason；`SupplierDetailDialog` 加「风险判定依据」区块（列出全部 reasons）。
- 性能：供应商量级几十家，全量算一次在毫秒级；接口加 60s 内存缓存即可，不需要物化表。

`suppliers.risk_level` 字段保留但不再作为颜色来源，降级为「人工加红」：
- 人工只能往严重方向改（绿/黄 → 红），不能把自动判出来的红刷成绿；
- 人工覆盖必须写备注 + 留痕，否则下次评审没人说得清为什么红。

## 7. P2 可选：把供需缺口按份额分摊到供应商（**2026-11-03 决定暂不实施**）

保留本节只为记录口径，避免以后有人重新提一遍。当时结论：地图只回答「这家能不能指望」，缺口去供需页看物料热力图，不在供应商身上再算一套。

现有供需口径是物料级（产能 = 该项目该物料所有供应商合计）。若需要定位「谁产能不够」，可另算一个**供应商自身供应系数**：

```
应承担需求 = 物料需求 × BOM × 该供应商本月份额%
自身系数   = 该供应商填报产能 ÷ 应承担需求
```

这只是「应该承担 vs 报了产能」的对比，不是现有供需结论，**必须另起字段、另起文案**，不能覆盖供需页数字。需要你确认要不要做。

## 9. 现在就会遇到的现实问题

真实库现状：6 家供应商、6 条供应关系、3 条项目供应关系，份额 / 库存 / 细分基本为空，**且 6 家都没有坐标**。

规则上线后预期：大部分供应商是**灰**（无份额、无库存），少数有供应关系但无台账的也是灰。这是正确结果，不是 bug。要让地图有颜色，得先补三样数据：份额台账（哪家占多少）、库存档案（在手 + 需求）、物料 BOM。

建议顺序：先补一个项目的完整三件套 → 看颜色是否符合直觉 → 再批量铺开。规则本身不用改。

## 10. 已确认口径（2026-11-03）

| 问题 | 结论 | 影响 |
|---|---|---|
| 独供默认颜色 | **黄**（Y2）；独供 + 库存跌破安全线才升红（R3） | 地图不会因单源多而一片红 |
| 供需缺口是否分摊到供应商 | **不分摊**。缺口只在供需页按物料看 | §7 的 P2 暂不实施，`supplier_risk.py` 不读 `capacity` |
| 人工打标 `risk_level` | **保留，且只允许加红**：绿/黄 → 红可以，红 → 绿/黄不允许；覆盖必须填备注 | 自动判定为主，人工是「踩刹车」不是「刷绿」 |

据此 P0 的最终输入：库存推算单元、份额台账（独供）、红黄牌、进行中的变更。
供需缺口按物料级参与——落到该物料在该项目下的全部供应商（用户接受「同物料 3 家一起红」的代价）。
变更单 `supplier_id` 有值只算那一家，为空则按物料推断（表单目前没有供应商字段，实际都走推断）。
