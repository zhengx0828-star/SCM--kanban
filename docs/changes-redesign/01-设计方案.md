## 0. 一句话定位

变更管理 = 记录「供需 / 份额 / 库存等稳态数据**被改变的过程**」，把一次变更拆成**可执行、可跟踪、可追责的任务树**，用甘特图 + 燃尽图 + 超期预警回答三个问题：

1. 现在有哪些变更在跑？（总量与分布 → Summary）
2. 每件事进行到哪了、谁负责？（甘特图 + 任务树）
3. 哪件事要黄了？（超期 / 临期预警 + 责任人）

## 1. 业务定位与边界

### 1.1 与现有模块的关系

| 模块 | 回答的问题 | 数据性质 |
| --- | --- | --- |
| 供需 / 份额 / 库存 | 现状是什么 | 稳态快照（当前值） |
| **变更管理** | **现状怎么被改的、改到哪了** | **过程数据（事件流）** |
| 规则页 | 口径与 SOP 是什么 | 文本 |

**设计原则（沿用项目已确立的口径）**：变更管理**不自动改写**其他模块的数据。它负责"过程记录 + 决策辅助"；变更结果是否落回主数据，由人确认（见 §13.2）。理由与地图/图表同源：数据保真，系统不替业务做未经确认的改动。

### 1.2 作用对象（锚点）

沿用「三层五表」，变更单的主锚点 = **项目 × 物料（PN）**，与库存推算单元、份额记录的锚定方式保持同构，便于后续横向联动。

| 维度 | 必要性 | 说明 |
| --- | --- | --- |
| 项目 | **必填** | 变更一定是"某个项目上的变更" |
| 物料 PN | **必填** | 用户明确要求；PN 是物料唯一键 |
| 供应商 | **可选** | 「替换供应商」「供应商涨价」这类变更本身就在改变供应商关系，强制绑定会自相矛盾 |

**待确认**：是否存在「项目级变更」（不绑具体物料，如项目整体排产调整）？→ §15-Q1

## 2. 概念模型：变更单 → 待办项 → 子项

这是本模块最核心的结构。用户描述的「甘特图里有待办项，待办项下面还有子项（如"提交报告"，下挂多份具体报告）」= 一个 **WBS（任务分解结构）**：

```
变更单 Change（项目 × 物料 × 变更类型）
  ├─ 待办项 Task ①  「提交报告」       负责人 / 计划起止 / 状态
  │    ├─ 子项 1.1  《样品测试报告》      ✓ 完成
  │    ├─ 子项 1.2  《产线验证报告》      ✓ 完成
  │    └─ 子项 1.3  《量产爬坡报告》      ○ 未完成
  ├─ 待办项 Task ②  「小批试产」       负责人 / 计划起止 / 状态
  └─ 待办项 Task ③  「量产切换确认」    负责人 / 计划起止 / 状态
```

- **待办项 Task** = 甘特图上的一根条，有工期、有负责人、有状态
- **子项 Subtask** = 交付物 / 检查项，以「完成 / 未完成」为主，可带轻量截止日
- 子项的存在让「提交报告」变成一个**可验收的集合**，而不是一句模糊的待办

### 2.1 层级实现方案对比（§15-Q3）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（建议）** | 单表自引用 `parent_id` + 显式 `level` 字段，**界面只开放 2 层** | 一表通吃、甘特树形渲染统一、结构上给未来留口子 | 统计需按 level 区分 |
| B | 两张表 `change_tasks` / `change_subtasks` | 语义直白 | 未来加层要动表结构 |
| C | 自引用且不限层 | 最灵活 | 报表/甘特复杂度上升，易被误用成无限嵌套 |

**建议 A**：结构上预留深度，产品上收敛为 2 层（任务 → 子项）。与库存页「受控枚举 + 兜底」的思路一致。

### 2.2 父任务完成度口径（§15-Q4）

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A | 父任务状态完全手动填 | 简单，但会与子项勾选状态打架（子项全勾了父项还显示"进行中"） |
| B | 有子项时，父任务完成度 = 子项完成数 ÷ 子项总数（自动，禁用父项手改） | 一致性好，但"部分完成"粒度粗 |
| **C（建议）** | **有子项 → 自动汇总；无子项 → 手动** | 与项目既有风格一致（`is_sole` 也是自动推导），且不损失灵活性 |

### 3.1 `change_types` 变更类型字典（页面可维护）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| code | str(50) UNIQUE | 类型编码 |
| name | str(100) | 类型名称（页面可增改） |
| category | str(50) | 分类：设计 / 工艺 / 供应商 / 成本 / 交付 / 其他 |
| color | str(20) | 甘特条与标签颜色 |
| default_owner | str(100) | 默认负责人（新建变更单时自动带出） |
| default_lead_days | int | 默认周期（天）→ 自动推算计划完成日 |
| is_active | bool | **停用而非删除** |
| sort_order | int | 排序 |
| remark | text | |

**删除策略**（对齐项目既有约定）：被变更单引用过的类型**只能停用，不能删除**，避免历史变更单出现孤儿引用。

### 3.2 `changes` 变更单

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| code | str(50) UNIQUE | 变更单号（生成规则见 §15-Q8） |
| project_id | FK projects | 必填 |
| material_id | FK materials | 必填 |

| requester | str(100) | 提出人 |

| status | str(20) | 见 §4 状态机 |
| priority | str(10) | high / medium / low |
| impact_level | str(10) | 影响等级（可选：影响交付 / 影响成本 / 影响质量） |
| plan_start / plan_end | date | 计划起止（甘特总条 & 整单预警依据） |
| actual_start / actual_end | date | 实际起止 |
| progress | int | 进度 %（口径见 §8.3） |
| risk_note | text | 风险说明 |
| is_removed | bool | 软删除（对齐 products/materials 约定） |
| remark | text | |
| created_at / updated_at | datetime | |

索引：`project_id`、`material_id`、`change_type_id`、`status`、`plan_end`（预警查询走它）。

### 3.3 `change_tasks` 待办项 / 子项（单表自引用）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| change_id | FK changes | 所属变更单 |
| parent_id | FK change_tasks, nullable | **NULL = 一级待办项；非空 = 子项** |
| level | int | 1 / 2（冗余，便于统计与渲染） |
| seq | int | 同级排序（甘特图自上而下顺序） |
| name | str(200) | 任务名（如「提交报告」） |
| description | text | 说明 |
| owner | str(100) | 责任人（预警要指名道姓，见 §10） |
| status | str(20) | todo / doing / done / blocked / cancelled |
| plan_start / plan_end | date | 计划起止（甘特条；子项可只填 plan_end） |
| actual_start / actual_end | date | 实际起止 |
| is_done | bool | 子项勾选 |
| done_at | date | 完成日（**燃尽图的唯一数据来源**） |
| weight | float | 权重（默认 1；可选填人天，用于加权进度） |
| remark | text | |
| created_at / updated_at | datetime | `updated_at` 也是「停滞预警」的依据 |

索引：`change_id`、`parent_id`、`plan_end`。

### 3.4 `change_type_tasks` 类型模板任务（**可选，但强烈建议**）

给变更类型预置"标准动作清单"：如类型「供应商切换」默认自带 4 个待办项（样品评估 / 小批试产 / 产线验证 / 量产切换）。

- **价值**：新建变更单时一键生成任务骨架，把录入从 30 分钟压到 3 分钟；同时让不同人做的同类变更**结构可比**
- **成本**：多一张表 + 类型管理界面里加一个任务清单编辑器
- **待确认**：§15-Q9

### 3.5 `change_logs` 变更日志（**可选**，审计时间线）

记录"谁在什么时候把状态从 A 改成 B"。供应链变更往往有追溯需求（为什么换供应商？谁批的？）。

- 只记三类：状态变更、负责人变更、计划日期变更
- 由后端自动写入，前端只读展示为时间线
- **待确认**：§15-Q11

### 3.6 迁移方式

新表走 `Base.metadata.create_all` 自动建；`migrations.py` 无需改动（它只处理"改已有表结构"的场景）。本次不修改任何既有表 → **对现存数据零风险**。

## 4. 状态机（§15-Q2）

### 方案 A：完整流程（5 态 + 3 分支）

```
草稿 → 评估中 → 执行中 → 验证中 → 已关闭
                 ↘ 已驳回 / 已取消
         执行中 → 已暂停 → 执行中（回环）
```

### 方案 B：轻量流程（3 态）

```
未开始 → 进行中 → 已完成（+ 已取消）
```

### 建议

**方案 A 的简化版**：`草稿 → 执行中 → 已关闭`，保留 `已暂停 / 已取消` 两个分支，**暂不做审批环节**（当前系统无登录、无角色，做审批会是空架子）。若后续需要审批，加 `评估中 / 待审批` 两态即可，结构与 A 兼容。

**状态与进度的关系**：状态为"已关闭"时进度锁定 100%；任务全部完成时**提示**是否关闭变更单（不自动关闭，避免误操作）。

## 6. 页面结构

```
/changes                        变更管理主页面
├─ 顶部：项目选择器（L0 全局 ⇄ L1 单项目，沿用现有页面选择器交互）
│
├─ L0 全局视图（未选项目）
│   ├─ 统计卡：变更总数 / 进行中 / 已超期 / 本周新增 / 涉及物料数
│   ├─ 分布图：按项目 ｜ 按变更类型
│   ├─ 全局燃尽图（全部在跑变更单的合并燃尽）
│   └─ 预警清单：超期 + 临期 Top N（含责任人、剩余天数）
│
├─ L1 项目视图（已选项目）
│   ├─ 统计卡 + 燃尽图（该项目）
│   ├─ 预警条：🔴 超期 3 ｜ 🟡 临期 5（点击筛选）
│   └─ 变更单列表（表格：单号/物料PN/类型/负责人/计划完成/进度/状态/预警）
│        └─ 点击行 → 右侧详情抽屉（Sheet）
│             ├─ 基本信息（可编辑）
│             ├─ 甘特图（任务树 + 子项，可折叠）
│             ├─ 任务清单（增删改、勾选子项、改责任人/日期）
│             └─ 变更日志时间线（若采纳 §3.5）
│
└─ 新建变更单 → Dialog（选项目 + 物料 + 类型 + 负责人 + 计划起止）
```

**对齐项目既有约定**：
- 空态统一整卡 `EmptyState`（沿用 `components/ui/empty-state.tsx`）
- 筛选器/选择器支持 **0/N**，不清空入口
- 详情用右侧 Sheet（项目已有 `InventoryDetailSheet`、`MaterialDrawerFilter` 的成熟模式）
- 默认值必须合法（避免 422，见 AGENT 约定）

## 7. 甘特图方案（§15-Q13）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（建议）** | **div / 绝对定位自绘**：左侧任务树（支持子项缩进、折叠），右侧时间轴 | 零新依赖（内网友好）、与 shadcn/Tailwind 风格一致、层级表达天然、交互自由 | 缩放与拖拽要自己写 |
| B | ECharts custom series | 项目已有 ECharts，导出图片方便 | 层级树 + 折叠要绕；时间轴刻度需手算；代码量大 |
| C | 第三方库（gantt-task-react / dhtmlx） | 功能现成 | **要加依赖**（内网安装成本高）、风格难统一、包体大 |

**建议 A**。理由：AGENT.md 明确"内网优先离线、先保证能跑"，加依赖是最高成本的一件事。

### 7.1 甘特图要素

- **行**：一级待办项 + 可展开的子项（子项缩进，条更细或仅显示"完成"节点）
- **条**：位置 = `plan_start ~ plan_end`；填充色 = 状态（未开始灰 / 进行中蓝 / 完成绿 / 受阻红）；条上显示完成度
- **今日线**：一条竖线标"今天"，超期条自然落在竖线左侧且未完成 → 一眼看出
- **时间粒度**：日 / 周 / 月 三档切换（默认按跨度自动选）
- **交互**：hover 显示 tooltip（任务名 / 负责人 / 计划起止 / 剩余天数）；点击条 → 打开该任务的编辑
- **范围**：默认 = min(plan_start) ~ max(plan_end) 自动外扩 3 天
- **拖拽改期**：方案 A 技术上可做，但建议放二期（成本高、易误操作）→ §14

## 8. Summary 与指标口径

### 8.1 你要的"每个项目有多少种变更 / 多少种变更类型"

这条需要拆分确认（§15-Q5），我理解的两个口径是：

| 指标 | 口径 | 呈现 |
| --- | --- | --- |
| **变更单数量** | 该项目下的变更单条数（可再按状态细分） | 数字 + 环比 |
| **变更类型覆盖数** | 该项目下出现过的 `change_type` 去重计数 | 数字 + 类型标签云 |
| **类型分布** | 每个类型各有多少张变更单 | 横向条形图 |

### 8.2 L0 / L1 指标卡

| 卡 | 口径 | 备注 |
| --- | --- | --- |
| 变更总数 | `count(changes)` | 可加"◷ 本月新增 x" |
| 进行中 | `status not in (已关闭, 已取消)` | 首期对齐 Dashboard 卡 5 |
| **已超期** | 整单 `plan_end < today` 且未关闭 | 红色，点击筛选 |
| 涉及物料 | `count(distinct material_id)` | L0 才有 |
| 预警任务 | 任务级超期 + 临期计数 | 与 §10 同源 |

### 8.3 进度口径（§15-Q6）

| 方案 | 算法 | 评价 |
| --- | --- | --- |
| A | 手工填 | 最省事，但与任务状态脱节 |
| **B（建议）** | **未加权：已完成一级任务数 ÷ 总一级任务数** | 直观、可解释 |
| C | 加权：`Σ(weight × 完成度) ÷ Σweight`（weight 默认 1，可填人天） | 精确，但要人填权重 |

**建议**：结构上按 C 实现（`weight` 默认 1，此时 C ≡ B），界面上默认展示 B 的结果，权重列可留空。

## 9. 燃尽图口径

### 9.1 定义

- **X 轴**：日期（变更单 `plan_start` → `plan_end`，超出自动延伸）
- **Y 轴**：剩余待办项数（或剩余工作量）
- **数据来源**：任务的 `done_at`（**只依赖已录入的数据，不推算、不补假点**）

### 9.2 线条方案（§15-Q7）

| 线 | 含义 | 画法 |
| --- | --- | --- |
| **计划线** | 理想进度 | 按各任务的 `plan_end` **阶梯下降**（更真实） |
| **实际线** | 真实进度 | 按 `done_at` 逐日累计下降 |
| 理想线（可选） | 线性基准 | 从总数到 0 的直线（作参照） |

**建议：计划阶梯线 + 实际线**，两条即可回答"我们比计划快了还是慢了"。不引入每日快照表（纯派生，零维护）——若未来需要"历史进度回放"，再加 `change_burndown_snapshots`。

### 9.3 口径分层（§15-Q7）

- 按**待办项数量**燃尽（默认，数据现成）
- 按**工作量（人天）**燃尽（需填 `weight`，可作为二期开关）

## 10. 预警机制（用户重点）

### 10.1 预警规则

| 级别 | 判定 | 配色 |
| --- | --- | --- |
| **已超期** | `plan_end < 今天` 且未完成 | 🔴 红 |
| **临期** | `0 ≤ plan_end − 今天 ≤ N` 且未完成（**N 默认 3 天**） | 🟡 黄 |
| **受阻** | `status = blocked`（与日期无关，主动标记） | 🔴 红（描边） |
| **停滞** | 任务 `updated_at` 超过 M 天无更新（M 默认 7） | 🔵 蓝，提示"该任务 N 天无更新" |
| 正常 | 其余 | ⚪ 灰 / 🟢 绿 |

- 阈值 N、M **不硬编码**：建议放一个轻量配置（页面「预警设置」入口），默认 3 / 7
- 一级与二级都参与预警（子项超期也要冒泡到父任务与变更单）
- **冒泡规则**：子项超期 → 父任务显示提醒 → 变更单列表行显示红点

### 10.2 预警呈现（三处，§15-Q9'）

1. **变更页顶部预警条**：`🔴 超期 3 ｜ 🟡 临期 5`，点击即筛选列表
2. **预警清单区**（L0 全局 / L1 项目内）：表格列出 `任务名 | 变更单 | 项目 | 物料PN | 负责人 | 计划完成 | 剩余/超期天数 | 级别`，按严重度排序
3. **Dashboard 卡 5**：从占位的 0 换成实时的"进行中变更单数"，并补 `onClick → /changes?status=active`

### 10.3 责任到人

预警行必带 `owner`；无责任人的任务**单独标灰提示"未指派"**——这是最容易漏的口子。

## 11. 数据上传（Excel 导入）

项目已有成熟的导入范式（`ExcelImportDialog` / `ShareImportDialog` / `InventoryImportDialog`），保持一致。

### 11.1 模板结构（§15-Q12）

| 方案 | 结构 | 评价 |
| --- | --- | --- |
| **A（建议）** | 两个 sheet：`变更单` + `待办项` | 层级与字段分离，清晰；一个变更单多任务时不用重复填表头 |
| B | 单个 sheet，靠"变更单号"列重复填充 | 一个 sheet 就够，但冗余行多、易错 |
| C | 只导入任务（变更单须先在页面建好） | 最简单，但手工前置工作多 |

`待办项` sheet 的层级表达：**`父项序号`列**——留空 = 一级待办项；填 `1` = 第 1 行一级任务的子项。

### 11.2 导入策略

- **幂等 upsert**：以 `变更单号 + 任务名` 定位；无变更单号的按 `项目 + 物料PN + 标题` 匹配
- **手改保护**：手工改过的字段打 `edited_manually` 标记，导入时不覆盖（**沿用份额模块已有机制**）
- **导入前置**：先校验（项目/物料/类型是否存在、日期合法），**列出错误行再决定是否导入**
- **结果摘要**：`新增 x 条 / 更新 y 条 / 跳过 z 条（含原因）`，与现有导入弹窗一致

### 11.3 页面内的其他录入方式

- 新建变更单 → Dialog
- 批量加任务 → 详情抽屉里支持"一行一个任务名"的批量粘贴框（比 Excel 更快，覆盖 80% 场景）

## 12. 页面内编辑能力矩阵（用户重点）

| 内容 | 编辑方式 | 理由 |
| --- | --- | --- |
| 状态 / 进度 / 负责人 / 完成勾选 | **列表行内即时改**（下拉 / 勾选 / 点击编辑） | 高频、每次只改一个字段，不能每次都开弹窗 |
| 变更单完整字段 | **右侧 Sheet 详情** | 字段多，需要空间与上下文（含甘特图） |
| 待办项 / 子项 增删改 | 详情 Sheet 内（行内编辑 + 拖拽排序） | 结构化编辑，需要看到父子关系 |
| 甘特条拖拽改期 | **二期** | 成本高、误操作风险大 |
| 变更类型维护 | 抽屉 / 弹窗（§5） | 低频 |
| Excel 批量 | 导入弹窗（§11） | 首次建档 / 批量迁移 |

**即时反馈约定**：任何修改都 toast 提示成功；失败给出中文原因（后端已有 Pydantic 中文兜底，新字段需登记到 `_FIELD_LABELS`）。

## 14. 分期建议

### 第一期（MVP，建议的范围）

1. `change_types` 字典 + 页面维护（增改停用排序配色）
2. 变更单 CRUD + 状态机（草稿/执行中/已关闭 + 暂停/取消）
3. 待办项 + 子项（2 层，勾选完成）
4. 甘特图（自绘，含今日线、状态配色、子项缩进折叠）
5. 燃尽图（计划阶梯线 + 实际线）
6. 预警条 + 预警清单（超期/临期/受阻，含责任人）
7. L0 / L1 双层视图 + Summary 卡 + 类型分布
8. Excel 双 sheet 导入 + 模板下载
9. Dashboard 卡 5 接入 + 侧边栏开通 + 规则页补 SOP

### 第二期（视使用反馈再定）

- 变更类型**模板任务**（一键生成任务骨架）
- 甘特条**拖拽改期**
- **变更日志时间线**（审计）
- **联动回写**（半自动应用到供应关系/份额）
- 导出（Excel / 图片）
- 燃尽图按**工作量**口径 + 历史快照
