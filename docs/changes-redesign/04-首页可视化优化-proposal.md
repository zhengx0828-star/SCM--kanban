## 1. 你的需求 1 ——「最需要盯的待办项」改为以变更单/项目为导向

### 现状
一张平铺表，行序 = `级别 → 超期天数降序`；列序 = `级别 | 任务 | 变更单 | 项目 | 物料 | 责任人 | 计划完成 | 天数`。
问题你说得对：**级别是第一公民，项目和变更单被埋在后面**，看一行不知道「这属于哪摊事」，而且同一个变更单的 3 个待办项被打散在表格不同位置（截图里 #1 的三行就散着）。

### 改法（我的推荐）
**列序重排 + 三级分组**：

```
▸ 储能系统集成项目                                  3 项待处理 · 最严重：超期 11 天   ← 项目组头（可折叠）

        已超期  供应商整改计划确认        郑工   计划 2026-09-25   ⚠ 超期 11 天
    #2 环氧板绝缘隔片耐压不合格整改 · 581601-000035                   1 项
        临期    供应商整改现场审核        陈工   计划 2026-10-07   剩 1 天
    #4 密封圈引入苏州江南精密密封为二供 · 570954-000071               1 项
        临期    技术协议签署              吴工   计划 2026-10-08   剩 2 天

        已超期  PPAP 全尺寸检测报告       张工   计划 2026-09-27   ⚠ 超期 9 天
        已超期  PPAP 材料成分报告         张工   计划 2026-09-29   ⚠ 超期 7 天
```

- **项目组头**：项目名 + 待处理项数 + 最严重级别色点 → 点一下折叠/展开（状态存 localStorage，与甘特图折叠同一套习惯）
- **变更单小标题**：`#id 标题 · PN`，右侧给该单的待办项数
- **任务行**：组内按级别严重度排（超期降序 → 临期升序 → 迟交降序）
- **保留「按严重度平铺」切换**（URL `?alerts=group|flat`，默认 `group`）——救火的时候还是「全库最严重的 8 条」最有用，这个视角不能丢

> ⚠ **这条我需要你确认口径**：你写的是「按照项目、任务、变更单、级别来排序」。我理解成「项目 → 变更单 → 任务，组内按级别」这个三级分组 + 列序也把项目/变更单提前。如果你其实只是要**排序**（不要分组），或者排序优先级真的是「项目 → 任务 → 变更单」，说一声我改。

### 附带的小改进
- 「展开全部」：现在硬截断 8 条，加一个按钮展开（或跳 L1）。分组后截断会切碎分组，改成**按整组保留**（宁可多显示一行，也不要把一个项目劈成两半）。

## 2. 你的需求 2 —— 首页加整体燃尽图

### ★ 这条必须动后端
`GET /api/changes/burndown` 现在**硬性要求** `change_id` 或 `project_id`，两个都不传直接 `400 需提供 change_id 或 project_id`。整体燃尽图没有这个接口。

后端改动（`backend/app/routers/changes.py`）：
- 两个参数都可为空 → **全局口径**（所有项目合并）
- 新增可选参数 `include_archived`（默认 `false`）
- 逻辑上就是删掉那个 400 + 复用现有的叶子聚合，**改动很小**

实测全局跨度：`plan_start` 2026-08-06 → `plan_end` 2026-11-04，**90 天，一天一个点**，横轴压力可接受。

### 前端
- `useChangeBurndown` 支持空参调用
- 卡片放 L0，**全宽**（燃尽图横轴 90 个刻度，塞进半栏会糊）
- 点数据超过 ~180 点时**按周聚合取样**（防将来数据量上来卡住），这一点写进实现

### 需要你拍板的口径
**归档单 / 作废单要不要算进整体燃尽？** 我的建议是**都不算**：
- 作废单按定稿 §4.2 本来就不参与任何统计
- 归档 = 项目做完了冻结。如果把归档单混进来，一个项目归档的瞬间曲线会突然「少掉一堆剩余」，看起来像进度暴涨，其实是假的
- 但这样有个副作用：归档项目的历史完成贡献也看不到了 → 折中方案是给个「含已归档」开关

## 3. 你的需求 3 —— 类型分布改成饼图

现状是横向进度条（每个类型一行）。改成**环形饼图（甜甜圈）**：

- 圆心显示**变更单总数**
- 图例带 `类型名 数量 张 · 百分比`
- **可点击扇区 → 下钻**：点「二供导入」→ 卡片墙只显示有该类型变更的项目（`project_overview` 里每个项目都带 `type_counts`，纯前端过滤即可，**不用加接口**），顶部出现「仅看：二供导入 ✕」的 chip

现在数据只有 3 个类型（二供导入 3 / 设计变更 1 / 质量问题 2），饼图会有点朴素，但等类型多了就有价值。

### 10.2 但"降级"不等于"丢掉"——自适应升降格

A 和 C 不是砍掉，是**做成会自己长大的指标**：

- **A 超期分档**：`≥3 个档位有值` → 自动升格为柱图；否则显示一行文字。数据一多它自己就出来了，不用再改代码
- **C 未指派**：常驻统计卡（不额外占位），`0` 时低调灰字、`>0` 时红字 + 可点击筛出

这是我建议的通用规矩：**指标只有一个值时，用文字；有结构时，才用图。**

## 11. 修订版版面（解决"一眼抓不住重点"）

### 11.1 核心手段：不是减图，是建主次

**问题不在"图多"，在"每张图一样大"。** 三条手段：

#### 手段 1：视觉权重分三级（用尺寸传递重要性）

| 级别 | 内容 | 老板的眼睛 |
| --- | --- | --- |
| **L 大卡**（占整行） | 整体燃尽图 | ★ 落点 |
| **M 中卡**（并排 2 张） | 类型饼图 · 项目饼图 | 扫一眼 |
| **S 小卡**（折叠区内） | 偏差榜 · 超期分档 | 需要时才看 |

#### 手段 2 ★ **每张图强制带一句「人话结论」**（本 proposal 的核心增量）

**这是"一眼抓住重点"的真正解法**：老板不需要"读图"，只需要**读一行字**。

| 图 | 自动生成的结论（示例，取自真实数据） |
| --- | --- |
| 整体燃尽图 | 「实际比计划慢 6 项，落后从 9/28 起持续扩大」 |
| 类型饼图 | 「6 成是二供导入（3/6 张）」 |
| 项目饼图 | 「动力电池 PACK 产线 3 张最多，且超期项最多（4 项）」 |
| 偏差榜 | 「乘用车电驱总成完成率 20% 垫底，落后最多」 |

有了这句，图的密度就不再是负担——**因为不需要看懂图就能拿到结论**。图只承担"让人信服"的角色，不承担"传达信息"的角色。

（结论必须由数据算出，不是写死的话术；无数据时给「暂无数据」而不是编一句。）

#### 手段 3：默认折叠 + 小屏塌陷

- 深度分析区（偏差榜 + 超期分档）**默认折叠**成一行，点开才展开
- 饼图区小屏自动塌成单列
- 待办项分组表默认 8 条 + 「展开全部」

### 14.3 ★ 意外修复：归档孤儿留痕（施工中查数据发现的）

排查「summary 的 `total` 从 7 变 8」时发现 `changes #3` 的 `archived_at` 是 NULL，但**归档留痕里还挂着一条它的"已归档"记录**。

根因：`unarchive_project`（取消整项目归档）只删 `scope == "project"` 的留痕。
于是「先单独归档某单 → 再整项目归档 → 再取消整项目归档」会留下一条**指向未归档单的孤儿留痕**，谎报状态。

修法（两道）：
- **写侧根治**：整项目取消归档时，连带清理「本次被取消归档的那些单」的 change 级留痕
- **读侧加闸**：`/archives` 只返回「目标确实还在归档态」的 `scope="change"` 留痕 —— **不删数据，只保证显示出来的一定是真的**（已验证：接口返回 0 条，库里原始行仍在）

### 15.4 一次完整的误判与纠正（方法论）

桌面截图里甘特图底部有根灰条，疑似多余滚动条。三步排查：① 量 `overflow-x:auto` 容器的 `scrollWidth/clientWidth` → 修 `range` 后 0 个可滚容器；② 量 `offsetWidth-clientWidth` → 全是 `2px`（1px 边框）与 `<html>` 自身滚动，**没有横向滚动条**；③ **判定性实验**：把 `overflow-x` 临时改 `hidden` 再截图 → **画面完全相同**。
→ 结论：**那不是滚动条**，是卡片自身装饰，与本次改动无关。
**教训：肉眼在缩略图上判断"这是不是滚动条"会误报。必须量 DOM，或做"改掉它看是否消失"的判定性实验。**

## 16. 第三轮：结论降级态的运行时覆盖（只读，不碰数据库）

**动机**：上一轮留了一条尾巴 —— 四个结论生成器（`burndownInsight` / `typeInsight` / `projectInsight` / `deviationInsight`）只做了**代码级**通读，因为真实库里只存在一种数据形状（**3/3 项目都滞后**），降级分支永远不被执行。而这类分支一旦上线命中，表现形式是**白屏或缺字**，属于最贵的那种缺陷。

### 16.1 手法：拦响应，而不是造数据

用 CDP `Fetch.enable` + `Fetch.fulfillRequest` 在**浏览器侧**把 `/api/changes/*` 的响应换成合成 payload：

```js
await send("Fetch.enable", { patterns: [{ urlPattern: "*/api/changes*", requestStage: "Request" }] });
// requestPaused → 按 URL 关键字返回合成 JSON（summary / project-overview / burndown / alerts / 列表）
```

为什么优于"往库里塞测试实体"：

1. **一个字节都不写数据库** —— 满足「造测试实体进正式库须先问用户」的约定，无需批准、无需清理；
2. 能构造现实中不存在的极端形状（如 `actual_remaining > plan_remaining` 且**差距持续扩大**）；
3. 跑完即走，可反复跑，适合做回归。

> ★ **坑**：`urlPattern` 必须是 `*/api/changes*`（尾部单个 `*`）。写成 `/api/changes/*` 会漏掉 `/api/changes?page=1` —— 它没有结尾斜杠，列表接口会直接穿透到真后端，让"空库降级"场景拿到真数据而**假失败**。

### 16.2 覆盖矩阵（8 场景 · 52 条断言 · `scripts/verify_degraded.mjs`）

### 17.2 口径改动：`total` = 有效单

改一处口径，**必须把所有消费方一起改**，否则立刻制造新的同屏矛盾：

| 位置 | 旧 | 新 | 不改会怎样 |
| --- | --- | --- | --- |
| 后端 `summary.total` | 未归档（含作废） | 有效单（`status != voided`） | — |
| 后端 `project-overview.total` | 未归档（含作废） | 有效单 | — |
| 后端 `change_done_rate` | `done / (total − voided)` | `done / total` | **重复减作废** → 乘用车 1−1=0 |
| 统计卡 hint | `进行中 6 · 已完成 1 · 作废 1` | `进行中 6 · 已完成 1 ｜ 另有作废 1` | 「6+1+1=8」与总数 7 打架 |
| 类型饼图结论 | 追加「另有 1 张作废未计入」 | 删掉 | 口径已统一，再交代就是噪音 |
| 项目卡「变更规模」 | `变更 N 张 · … · 作废 1`（连排） | `变更 N 张 · 进行中 a · 已完成 d ｜ 另有 作废 1` | 读者会把作废当成 N 的构成 |
| 项目饼图 `metric=tasks` | `total − voided − archived` | **新字段 `open_tasks`** | **重复减作废**（1−1−0=0，静默缺项） |
| 偏差榜可见性 | `total − voided > 0` | `total > 0` | 同上，只剩作废单的项目会被误判成空 |
| 卡片墙「有单」判定 | `total > 0` | `total + voided > 0` | 只剩作废单的项目会**凭空从墙上消失** |
| 归档弹窗张数 | `total` | `total + voided` | 后端归档**连作废单一起冻**（只按 `archived_at` 过滤），少报 |

设计原则：**作废单不是「构成」，是「另有」**。凡是「总数 = 分项之和」的地方，作废都必须站在加法之外，用分隔符隔开、加「另有」二字。

### 17.3 真缺陷（用户视角可见，非本轮引入）

**A. 「待办项」同屏两个数**

真实数据下：统计卡「待办项」= **33**（`task_state_counts` 全量，含按时完成 1 + 迟交完成 11），项目饼图「待办项数」= **21**（各项目 `open_tasks` 之和）。同一个词、同一屏、两个数。

**B. `/materials` 的无效 HTML 嵌套**

`<button>` 套 `<button>`，共 6 处（3 张项目卡 × 2 个图标按钮），另有 1 处物料行（在「物料」Tab 下）：
