## 三、本轮发现并修复的 3 个缺陷

### 1. 「自动完成」只在单一事件点评估 → 假完成 / 假未完成（后端）

- **现象**：播种脚本按真人顺序（建一条、勾一条）写数据，落库统计出现 `active=1 / done=5` 的荒唐分布。
- **根因**：`_refresh_change_summary(auto_complete=True)` 只在「勾选那一刻」评估一次。单子当时只有 1 个任务 → 勾上即 `done`；**随后再加新任务，状态仍停在 `done`**。反之，删掉最后一条未完成任务也不会自动 `done`。
- **修复**：新增 `_sync_status_from_tasks()`，任何任务变化（增/删/勾/取消勾）后同步一次：叶子全勾→`done`、有未勾→`active`、**无叶子则不动**（保留手动设置）；作废单与归档单不参与。
- **验收**：加回一条未完成任务 → 状态回落 `active`；删完未完成任务 → 自动 `done`。

### 2. 导出 Excel 的「变更单」sheet 全部数据挤在第 1 行（后端）

- **现象**：导出的 `变更单` sheet 只有 1 行，表头被最后一张单的数据覆盖。
- **根因**：`ws1.append([])` 在 openpyxl 里**不会真的产生一行**（空列表没有单元格），`ws1.max_row` 始终停在表头行 1；而写值用的是 `ws1.cell(row=ws1.max_row, ...)` → 每张单都写在第 1 行互相覆盖。
- **修复**：改用显式行游标 `row1`，逐行递增。修复后导出 9 行 × 18 列，内容与库内完全一致。
- **注意**：模板端点（`/api/changes/template`）用的是显式 `row=` 且只写固定几行，**不受此 bug 影响**。

### 3. `?risk=` 筛选把作废单算进来，与卡片数字对不上（后端）

- **现象**：卡片/项目墙说「超期 4 张」，而 `GET /api/changes?risk=overdue` 返回 5 条。
- **根因**：`risk` 过滤未排除 `voided`，而 `summary` / `project-overview` 按定稿 §4.2「作废单不参与任何统计与预警」已排除。
- **修复**：`risk` 过滤默认跳过作废单；**例外**：显式传 `status=voided` 时不过滤（否则"查作废单的超期项"永远返回空）。
- **验收**：`risk=overdue` → 4 条（= 卡片）；`risk=overdue,near` → 5 条；`status=voided&risk=overdue` → 1 条。

## 四、测试过程中的一次数据污染（已复原，记教训）

写测试脚本第 2 项时，把**变更单 id 当任务 id** 传给 `/api/change-tasks/{id}/toggle`。该 id 恰好是**另一张单**下的真实任务，后端不报错，静默把它勾上了（导致 C1 完成率从 28.6% 变 42.9%）。

- **发现方式**：事后按 id 反查归属、比对 `done_at` 时间戳（`22:58:26` 明显是刚刚被写的）。
- **复原**：`toggle false` → `done_at` 清空、完成率回到 28.6%。
- **规矩**：**跨实体引用 id 必须先校验归属**（先取父实体的详情、从它自己的子列表里拿 id），并且测试脚本对"不可预期成功"的调用要断言业务语义而不只是状态码。已补进测试脚本（新增「任务归属校验」断言）与技能库。
