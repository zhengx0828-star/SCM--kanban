## 0. 一句话定位

客户会改需求（V1.0 → V2.0）。本方案把「客户需求」从**就地覆盖的一个字段**升级为**只增不改的版本快照序列**，由唯一的「当前版」指针驱动全站供需计算。

**产能与 BOM 恒定不变、不参与版本化** —— 这是本方案的边界铁律，也是它能做得这么轻的原因。

要回答的三个问题：

1. 这版需求跟上一版差在哪？ → 版本对比（双线叠加 + 差异表）
2. 现在这张图是按哪一版算的？ → 全站版本徽标
3. 换版之后缺料风险是变好还是变坏？ → 风险对比（产能不变 ⇒ 系数直接跟着需求走）

## 1. 边界与原则

### 1.1 什么参与版本化

| 数据 | 归属 | 版本化 | 说明 |
| --- | --- | --- | --- |
| 客户需求 `demand` | 项目级 | ✅ **唯一对象** | 客户改版的对象；1-12 月一整份快照 |
| BOM 用量系数 `bom_factor` | 项目 × 物料 | ❌ | 用户确认：不随版本变 |
| 供应商产能 `capacity` | 物料 × 供应商 | ❌ | 用户确认：不随版本变 |
| 份额 / 库存 / 变更单 | — | ❌ | 与本方案无关，不做任何联动 |

### 1.2 由「产能不变」推出的一条推论（★ 施工时别漏）

因为 **BOM 与产能恒定**，任何一次版本切换都只动需求侧：

```
物料需求 = 客户需求 × BOM     → 随版本等比缩放（BOM 不变）
供应系数 = 产能 ÷ 需求         → 版本一变，系数立刻变（产能不变）
```

**结论：版本对比天然就是「风险对比」。** 不需要为它新增任何字段或接口 —— 同一份产能、两版需求，把系数算两遍就出来了（复用 `frontend/src/lib/supply-risk.ts` 既有口径函数）。这是本方案性价比最高的一处设计，不要漏做。

### 1.3 四条硬原则

1. **只增不改**：任何一次"保存需求"都生成新版本；历史版永久只读，不可编辑、不可删除。
2. **不造假数据**：不预置演示版本；需求为空的项目**不生成** V1.0（保持"未录入"空态）。
3. **不破坏既有消费方**：版本表为准，同时把当前版**投影回写**到旧字段（§3.3），让 6 处既有消费方零改动继续跑。
4. **老数据零丢失**：迁移只「读取 → 插新行」，不 UPDATE 既有字段、不 DELETE 任何行。

## 3. 数据模型

### 3.1 新表 `project_demand_versions`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Integer PK | |
| `project_id` | FK `projects.id` ON DELETE CASCADE | 版本属于项目 |
| `seq` | Integer NOT NULL | **项目内自增**；排序与"上一版"判定一律用它 |

| `source` | String(16) NOT NULL | `manual` / `excel` |
| `effective_date` | Date NULL | 生效日期 |
| `is_current` | Boolean NOT NULL default 0 | 当前版标记 |
| `note` | Text NULL | 备注 |
| `created_by` | String(64) NULL | 录入人（系统无登录体系，纯文本留痕） |
| `created_at` / `updated_at` | DateTime | |

### 3.2 约束

- `UNIQUE(project_id, seq)`
- **部分唯一索引**保证同项目至多一条当前版（沿用 `models.py` 里 `uq_products_sku_active` 的同款写法，**不引入新依赖**）：

```python
Index("uq_demand_version_current", "project_id", unique=True, sqlite_where=text("is_current = 1"))
```

- `Index("ix_project_demand_versions_project_id", "project_id")`

### 3.3 与旧字段 `project_supply_relations.demand` 的关系（★ 关键）

**不删列、不废弃，改为「当前版的投影」。**

| 载体 | 角色 |
| --- | --- |
| `project_demand_versions` | **唯一真相源**（source of truth） |
| `project_supply_relations.demand` | 当前版的**投影副本**，后端写版本时同步回写 |

理由：`demand` 目前被 **6 处消费方**读取 ——

1. `SupplyDemandPage` 风险总览与明细聚合
2. `ProjectSupplyDetailPage` 需求卡与物料聚合
3. `MaterialDetailDialog`
4. 库存信号塔按 BOM 折算需求
5. `DemandExcelImportDialog`
6. `DemandLineChart` 数据源

保留投影 ⇒ 这 6 处**不改也能正确**，版本化成为"叠加能力"而不是"重写工程"，一次性把回归风险压到最低。后续若要彻底切换，只需改 `useProjectsRelations` 一处数据来源即可。

## 4. 口径定义

### 4.1 「当前版」的唯一判定

```
当前版 = 该项目下 is_current = 1 的那一条（部分唯一索引保证至多一条）
兜底  ：项目首版创建时自动置 is_current = 1，杜绝"无当前版"的项目
```

全站供需计算**只读当前版**，不存在"自动取最大版本号"之类的暗规则。

### 4.2 版本对比

```
Δ(月)   = 新版[m] − 旧版[m]
Δ%(月)  = Δ / 旧版[m] × 100%     （旧版[m] = 0 → 显示「新增」，不计算百分比）
年合计  = Σ12 个月，单独给出绝对变化与百分比
```

默认对比对象 = 上一版（`seq` 小一号的最新一版）；也支持任选两版。

### 4.3 风险对比（产能恒定带来的免费收益）

同一物料、同一月份：

```
系数_旧 = 产能 ÷ (旧版需求 × BOM)
系数_新 = 产能 ÷ (新版需求 × BOM)
风险迁移 = 旧状态 → 新状态（缺口 <1.0 / 紧张 1.0-1.3 / 充足 >1.3）
```

差异表中突出展示「**由充足/紧张 变为 缺口**」的物料 × 月份 —— 这是最需要一眼看到的那一格。

### 4.4 颜色语义（写进规则页）

| 变化 | 颜色 | 语义 |
| --- | --- | --- |
| 需求**上调** | 红 | 供应压力变大 |
| 需求**下调** | 绿 | 压力减轻 |
| 不变 | 灰 | — |

> 与系统既有语义一致（缺口 = 红）：需求上调 → 更可能缺料 → 红。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/projects/{id}/demand-versions` | 版本列表（含 `is_current`、`seq`、`version_no`、`label`、`year_total`） |

### 6.1 需求录入区版式（2026-10-16 定稿，已过 Demo 验证）

**月份横排一行，下面一行各对应需求** —— 即横读是月份、纵读是各月需求：

```
1月   2月   3月   4月   5月   6月   7月   8月   9月  10月  11月  12月
[400] [420] [450] [460] [480] [470] [540] [620] [700] [860] [920] [1000]
```

- 12 列等宽栅格（`grid-template-columns: repeat(12, 1fr)`），每月单元格 = 月份标签 + 数值输入框，月份标签右对齐、输入框数值右对齐 + `tabular-nums`。
- **改动过的月份**整格浅红底 + 红边描出（`changed`），扫一眼就知道哪几个月动过；方向与幅度看下方「版本对比」的差异表。
- 与「版本对比」差异表的分工：**上面负责录，下面负责比** —— 逐月 Δ / Δ% / 风险迁移只在差异表里出现，录入区不重复输出，避免两处口径打架。
- 历史版本：输入框禁用置灰，版本条上给「历史版本 · 只读」提示。
- ⚠️ 反面案例留痕：曾一度改成「月份为行、1-6月/7-12月两栏并排」的表格，**已废弃** —— 需求录入要的是「月份横排」的整年一览感，不是列表。

### 6.2 版本对比差异表版式（2026-10-16 定稿，已过 Demo 验证）

**同样是「月份横排一行，下面各对应数值」** —— 与录入区保持同一种阅读方向，视线不用换向：

| 指标 | 1月 | 2月 | … | 6月 | 7月 | … | 12月 | 年合计 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| V1.1（对比版） | 400 | 420 | … | 500 | 520 | … | 780 | 6,470 |
| V2.0（当前版） | 400 | 420 | … | 470 | 540 | … | 1,000 | 7,320 |
| Δ | — | — | … | **-30** | **+20** | … | **+220** | **+850** |
| Δ% | — | — | … | **-6.0%** | **+3.8%** | … | **+28.2%** | **+13.1%** |

- **列为月份（1-12 月 + 年合计），行为指标**；年合计落在最右侧一列，不再单起一行。
- 当前版那一行行名加粗，便于和对比版区分。
- Δ / Δ% 单元格按**符号**着色：**正=红、负=绿**。**不写「上调 / 下调」这类文字** —— 正负号本身就是语义，不占横向空间、也不用读词。
- 表外层套 `overflow-x:auto` + `min-width:880px`，窄屏横向滚动，不挤压列宽。
- ⚠️ 反面案例留痕：**「月份为行」的竖表已废弃** —— 12 行的竖表既占高度，又和录入区的横排方向打架；**「变化」行也已废弃**（内容与 Δ% 行完全重复）。

### 6.3 版本选择器：折叠下拉（2026-10-16 定稿，已过 Demo 验证）

版本条**不用平铺 chip**，收成一个**折叠下拉**；下拉里**只有版本**，不再展示版本说明 / 来源 / 生效日期 / 录入人 / 创建时间这排元信息。

**收起态（触发器）**：`V2.0` + `当前` 徽标 + 版本说明 + ▾（查看历史版时徽标变 `只读`）

**展开态（面板）**：一版一行，倒序排列（新版在上）

| 版本 | 说明 | 相对上一版 |
| --- | --- | --- |
| V2.0 `当前` | 客户 10 月调产（Q4 上量） | **+13.1%** |
| V1.1 | 客户 8 月更新 Q4 预测 | **+5.5%** |
| V1.0 | 初始版 / 客户 FY26 预测 | 初始版 |

- 每行右侧给**该版相对上一版的年合计变化百分比**：**直接写 `+xx.x%` / `-xx.x%`，不写「上调 / 下调」文字**；首版无对比对象时显示「初始版」。
- 面板底部两条动作：`新建版本（复制当前版）`；当查看的是历史版本时额外出现 `设为当前版`。
- 点击面板项 = 切到该版本查看（并收起面板）；**点击面板外部自动收起**。
- ⚠️ 元信息不再显示（用户要求「只有版本」）。字段仍保留在数据模型里（`source / effective_date / created_by / created_at`），需要时可随时放回下拉项副行。
- ⚠️ **实现坑（务必注意）**：卡片默认 `overflow:hidden` 会把绝对定位的下拉面板裁掉 —— 需给宿主卡片加 `overflow:visible`（与 `SupplyDemandPage` 里 `MultiSelectDropdown` 的既有坑同源）。

### 6.4 版本信息落在页面的哪（2026-10-16 定稿，已过整页 Demo 验证）

版本链是**项目级**的，所以「落点」分两页共 5 处：

| 落点 | 页面 | 位置 | 放什么 |
| --- | --- | --- | --- |
| ① | 供需管理首页 | **项目卡片**内新增一行 | `需求版本 V2.0` + 生效日期 + 较上版 `+850 · +13.1%`；首版显示「首个版本」。点卡片进详情 |
| ② | 供需管理首页 | **明细分析 · 客户需求**的图例 | 每个项目一行：`PRJ-2601 新能源电驱总成 A` + `当前 V2.0` 徽标 |
| ③ | 项目详情页 | **顶部客户需求卡** | 版本折叠下拉（§6.3）+ 12 月横排录入（§6.1） |
| ④ | 项目详情页 | 需求卡下方**新增「版本对比」卡** | 折线（当前版实线 / 对比版虚线）+ 转置差异表（§6.2） |
| ⑤ | 项目详情页 | **风险对比卡** | 产能与 BOM 恒定下的风险迁移表；表下注明口径 `PRJ-2601 需求 V1.1 → V2.0` |

- **首页「风险总览」不动** —— 它是全项目汇总，且各项目版本本就可能不同，挂不出单一版本号（见 §6.5）。

### 6.5 多项目口径（★ 容易出错，务必遵守）

**每个项目一条独立版本链，因此「当前版」是逐项目的，全站不存在统一的版本号。** 举例：PRJ-2601 已到 V2.0、PRJ-2602 已到 V2.0、PRJ-2603 还停在 V1.0。

由此推出三条硬规则：

1. **汇总视图不说单一版本号。** 风险总览、明细分析的聚合口径，措辞必须是「**各项目按各自当前版**」，不能写「基于需求 V2.0」——那会让人误以为全站同版。
2. **凡是逐项目展示的地方，必须带出该项目自己的版本号。** 项目卡片（落点 ①）、客户需求折线图例（落点 ②）都属于此类。
3. **明细分析的版本徽标按选择情况分三态**：

| 选择情况 | 徽标文案 |
| --- | --- |
| 只选 1 个项目 | `PRJ-2601 · 需求 V2.0` |
| 选了多个、且当前版一致 | `3 个项目 · 均按需求 V2.0` |
| 选了多个、但版本不一致 | `3 个项目 · 版本不一（V2.0 / V2.0 / V1.0）`，并在图例逐项目标出 |

4. **切换项目 = 切换一整套版本上下文。** 详情页的版本下拉 / 对比基准 / 风险对比 / 「另存为新版本」全部跟着项目走；项目只有一个版本时，对比与风险区给**空态文案**（「本项目只有 1 个版本，暂无可对比的历史版本」），不要空白也不要报错。

## 7. 迁移与数据安全

启动时在 `backend/app/migrations.py → run_migrations` 内新增 `_migrate_demand_versions`，**幂等**：

```
1. 若 project_demand_versions 不存在 → 跳过（建表由 main.py 的 create_all 负责）
2. 对每个 demand 非空的项目：
     - 该项目已有版本记录 → 跳过（幂等）
     - 否则插入一条：seq=1, version_no='1.0', label='初始版',
                    demand=<现有 JSON>, source='manual', is_current=1
3. demand 为空 / NULL 的项目 → 不生成版本（保持"未录入"空态）
```

**数据安全承诺**：只读旧值、只插新行；**不 UPDATE 任何既有字段、不 DELETE 任何行**。跑完 `products.db` 老数据一行不少，跑一次与跑十次结果一致。

## 9. 被排除的选项（留痕，避免以后重复讨论）

| 选项 | 为什么不用 |
| --- | --- |
| 项目×物料级版本 | 客户给的是产品总需求（项目级），粒度下沉会让"改一个物料"产生版本链分叉，录入与对比都翻倍复杂 |
| 自动取最大版本号 / 按生效日期判定当前 | 客户改版必须由人负责发布；暗规则一旦被手填版本号破坏，全站算错且无人察觉 |
| 草稿 + 发布两态 | 单人使用场景，草稿态的复杂度换不来收益 |
| BOM / 产能版本化 | 用户确认二者恒定；且产能是**供应商级**主数据，版本化会把它强行下沉到项目级，破坏现有三层模型 |
| 把需求版本塞进变更管理 | 变更管理管"过程 / 任务 / 超期"，需求版本管"数据快照"；锚点（物料 vs 项目）与生命周期都不同 |
| 为版本对比新增后端接口 | 产能与 BOM 恒定 ⇒ 对比纯属计算；前端已有 `supply-risk.ts` 口径函数，加接口是纯浪费 |
