## 1. 现状：四处预警、四套分级、四个页面

| 来源 | 位置 | 现有类型 | 判定在哪儿算 |
| --- | --- | --- | --- |
| 供需 | `/supply-demand` 供应系数热力图 | 缺口 / 紧张 / 充足 / 无数据 | **纯前端** `lib/supply-risk.ts` |
| 库存 | `/inventory` 顶部四卡 + 每行产能占用 | 耗尽 / 紧急 / 偏低 / 充足 / 无法评估；超出额度 / 紧张 / 充足 | 后端 `_doh_bucket_of`、`INV_CAPACITY_*` |
| 变更 | `/changes` 预警表 + 项目卡墙边框 | 超期 / 临期 / 迟交 | 后端 `_task_state` |
| 份额 | `/share` 风险排行 | 独供 / 波动 / 偏差 / 错配 | 后端 `_risk_chain_type` |

四处各自有分级（`high/medium`、`overdue/near/late`、`stockout/urgent/low`、`shortage/tight`），互相不可比，所以只能分四页看。

## 2. 先说清楚不做什么

| 不做 | 理由 |
| --- | --- |
| 不建预警表 | 预警是派生数据。落库 = 每天要和源数据对账，还会出现「源数据已修好、预警还红着」。 |
| 不做已读 / 忽略（v1） | 「已读」与实时状态天然冲突：标了已读、数字还在。确有噪音时再上 `alert_mutes`（指纹 + 到期日），不进 v1。 |
| 不做消息推送 | 无账号体系、内网单机，推给谁都是问题。 |
| 不重算任何口径 | 全部同进程 import 现有函数，**一行判定逻辑都不复制**。 |
| 不做指派 / 关闭 | 处理动作本来就落在源模块（变更勾任务、库存补录入库、份额重录），预警中心只负责"指向"。 |

## 3. 五个来源 · 十三个类型 · 三级严重度

### 3.1 分级原则

- **P0 已发生**：数量已经不够，或已经逾期。今天不动就出事。
- **P1 将发生**：有明确时间窗，或有结构性缺陷，或**数据缺口让预警整体静默**。
- **P2 偏离**：已完成但迟、口径在恶化、可延后处理。

### 3.2 映射表

| 来源 | kind | 判定 | 级别 | 复用函数 |
| --- | --- | --- | --- | --- |
| 供需 | `shortage` | 系数 < 1.0 | P0 | `riskStatusOf` |
| 供需 | `tight` | 1.0 ≤ 系数 ≤ 1.3 | P1 | 同上 |
| 库存 | `stockout` | 今日 DOH ≤ 0 | P0 | `_doh_bucket_of` |
| 库存 | `urgent` | DOH < 安全天数，或 DOH < 3 天 | P0 | 同上 |
| 库存 | `low` | 安全天数 ≤ DOH < LeadTime | P1 | 同上 |
| 库存 | `cap_short` | 项目额度占用 > 100% | P1 | `INV_CAPACITY_SHORT` |
| 变更 | `overdue` | 计划完成日已过且未勾 | P0 | `_task_state` |
| 变更 | `near` | 距计划完成 ≤ 临期窗口 | P1 | 同上 |
| 变更 | `late` | 已勾但晚于计划日 | P2 | 同上 |
| 份额 | `sole` | 同项目同物料仅 1 家供应商 | P1 | `_risk_chain_type` |
| 份额 | `fluctuation` | 环比 ±30% | P1 | 同上 |
| 份额 | `deviation` | ｜本月 − 上月建议｜ > 5pt | P2 | 同上 |
| 份额 | `mismatch` | 份额 ≥ 50% 且加权分 < 0.5 | P2 | 同上 |
| 数据 | `missing_input` | 缺需求 / BOM = 0 / 需求为 0 | **P1** | `_unknown_kind` |
| 供应商 | `supplier_risk`（**未接入**） | `suppliers.risk_level` = red / yellow；规则待定，当前人工打标 | 待定 | 暂无 |

### 3.3 两个刻意的决定

**① 数据缺口放 P1，不放 P2。**
缺需求或 BOM = 0 时，供需页判「无数据」（灰）、库存页判「无法评估」（灰卡），两处都不报警——**等于假绿**。它比任何单条 P0 更危险，因为会让人以为没事。这是我觉得最该被聚合的一类。

**② 数据缺口按「项目 × 成因」聚合成一条，不是一行一个单元。**
否则 40 个推算单元缺 BOM 就刷 40 条，把 P0 淹了。文案形如：`LFP3 · 3 个物料缺 BOM 系数 → 供需与库存预警未生效`。

## 4. 接口契约

```
GET /api/alerts?project_ids=1,2&base_month=2026-10&horizon=3&severity=&source=
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `project_ids` | 空 = 全部 | 逗号分隔 |
| `base_month` | 最新有份额数据的月份 | 份额口径的基准月，显式化，避免"本月"歧义 |
| `horizon` | 3 | 供需只看基准月起 N 个月；0 = 全年 12 个月 |
| `severity` | 空 = 全部 | `p0` / `p1` / `p2`，可多值 |
| `source` | 空 = 全部 | `supply` / `inventory` / `change` / `share` / `data`，可多值 |

```json
      "ref": { "project_id": 1, "material_id": 12, "pn": "PN 123", "month": "2026-11" }
    }

```

### 4.2 字段约定

| 字段 | 用途 |
| --- | --- |
| `fingerprint` | 稳定标识。同一问题重复出现时值不变，供前端做 key、将来做「忽略」的锚点 |
| `as_of` | **每条自带时间口径**。份额是月快照、库存是今日、变更是今天、供需是某月——不允许页面统一写"本月" |
| `impact` | 排序用的量。**单位因 kind 而异**（件 / 天 / 百分点 / DOH），只在同 kind 内可比 |
| `ref` | 结构化引用，前端统一由 `buildAlertLink(ref, kind)` 生成 URL，后端不返回路由字符串（避免后端耦合前端路由） |
| `thresholds` | 阈值单一真相源在后端，随响应下发；前端图表改用响应里的值着色，不再硬编码 |

### 4.3 排序

```
severity 升序 → kind 固定序（供需 > 库存 > 变更 > 份额 > 数据）→ impact 降序 → fingerprint
```

`impact` **不跨 kind 混排**——4440 件和 6 天没有可比性，混排会得出荒谬结果。

| --- | --- | --- |

### 5.2 Dashboard 第一屏与预警中心的分工

**一句话：Dashboard 答「哪块红」，预警中心答「哪几条红」。老板看完 Dashboard 就可以走人，要走细才点进预警中心。**

现在的 5 张卡是平行铺开的 KPI，解决不了「哪里有问题」，有五个具体毛病：

| # | 问题 | 证据 |
| --- | --- | --- |
| 1 | 第一位放的是存量数字 | 第一张卡是「项目/物料总数」，不表风险、不可点，却占最大视觉权重 |
| 2 | 风险项用了健康色 | 「份额波动物料」色条是 `bg-emerald-500`（`DashboardPage.tsx:242`），绿色在供应链语境 = 没事；隔壁「独供」却是 `bg-red-500` |
| 3 | 五个数字四套单位 | 项目数 / 物料数 / 推算单元数 / 变更单数，并排会被误读为可比较、可相加 |
| 4 | 两种严重度被加成一个数 | 「库存天数 < 3」= `stockout` + `urgent` 相加，老板看不出已经断了几条 |
| 5 | 六次独立请求、五个口径 | suppliers / projects / materials / share-stats / inventory-overview / changes-summary；再加 `/api/alerts` 就是第七个来源，必然对不上 |

**改法：三段结构**

```
① 结论条（一行，P0=0 时转绿）
   ● 3 条已发生风险，影响 2 个项目 · 另有 6 条 3 个月内发生
     供需 1 · 库存 1 · 变更 1                     最急：PN 123 侧板 11 月只能满足 63%     [查看全部 9 条]

② 项目风险热点矩阵（项目 × 5 维度 + 金额敞口）
                                  供需  库存  变更  份额  数据缺口  金额敞口
   LFP3 储能电芯          ●1    ●2    ●1    ●2    ●1        —
   NPI-2 新品导入          —     ●1     0    ●1     —        —
   TV-M 电视主板           0      0     0     0     —        —

③ 整体指标（原 5 卡降级为一行 5 格，放地图下方）
```

- **结论条**：全站唯一的「有没有事」答案。文案用人话，不出现「供应系数 1.08」这类术语，改写成「只能满足 63% 需求」。
- **矩阵**：老板真正需要的视图——按**位置**（项目）组织，不按模块组织。格子 = 该类信号的最高严重度 + 条数，点格直接落到预警中心已过滤列表。灰格「—」= 该维度无数据，**不等于健康**，脚注写明。
- **金额敞口列先留白**：这是老板接着要问的第二个问题，等成本模块上线才有数。留空比编一个数诚实。
- **原 5 卡降级**：不再与风险混排。「项目/物料」「供应覆盖」是存量体检，「独供」「库存 < 3 天」「变更进行中」带状态色。色条语义统一为一套：红 = 已发生，琥珀 = 将发生，绿 = 正常，灰 = 无数据。

**取数：Dashboard 顶部不新增数据源，全部读 `/api/alerts` 的 `by_project` 块。**
这是本节最关键的约束——否则首页说 3 条、预警中心说 4 条，老板当场发现，整套系统的可信度就没了。改造后 Dashboard 的请求数从 6 降到 1（地图与供应商点位仍单独取，与风险无关）。

**不做趋势线**：想知道「在变好还是变坏」需要每天存一张计数快照，现在没有历史，v1 不做，也不要用前端算出来的假趋势。

## 7. 已知风险

| 风险 | 对策 |
| --- | --- |
| **口径漂移**（最怕的：预警中心说 3 条、库存页说 2 条） | 全部 import 现有函数；供需单独做 parity 脚本 |
| **性能**：`_assemble` 会算 30 天完整矩阵，只为拿桶号 | v1 直接复用（数据量小、SQLite 单机）；留 TODO，超过 500 单元再拆轻量路径 |
| **时间基准不一致**：份额是月、库存是日 | `base_month` 显式参数 + 每条 `as_of` 标签，页面不出现裸"本月" |
| **告警疲劳**：一个项目缺 BOM 刷出几十条 | 数据缺口按「项目 × 成因」聚合；其余按「项目 × 物料 × 月」聚合，同 kind 同实体只留最严重的一条 |

## 8. 分四批，每批可独立验收

| 批次 | 内容 | 验收方式 |
| --- | --- | --- |
| 1 | `/api/alerts` 后端 + 契约（含 `by_project` 块） | `curl` 输出对比现有四页数字，逐条对齐 |
| 2 | `/alerts` 页面 + 侧边栏红标 | 截图核对分组、排序、跳转后过滤是否生效 |
| 3 | Dashboard 第一屏改三段（结论条 / 热点矩阵 / 指标降级） | 截图核对：首页 P0 数与预警中心一致；点格后列表条数 == 格子数字 |
| 4 | `thresholds` 回传 + 前端图表改读后端 | 改一个阈值（如 1.3 → 1.4），确认热力图与预警中心同步变 |

> Dashboard 拆成独立批次，是因为它要删改现有 5 卡，风险与预警中心页面不同源，混在一起出问题不好定位。

## 9. 需要你确认的四件事

1. **独立页面 `/alerts`，还是并进 Dashboard？** 我倾向独立页面——聚合的价值在"一次看全 + 能跳"，塞进 Dashboard 会让首页继续变长。
2. **已读 / 忽略要不要做？** 我建议 v1 不做。
3. **数据缺口进不进 v1？** 我建议进，且定 P1。
4. **Dashboard 顶部接受改成三段吗？** 这会删掉"项目/物料总数"的卡位（降级到地图下方），并把「库存 < 3 天」拆成"已断货 / 紧急"两个数。现有 5 卡的跳转全部保留，只是改到预警中心落地。
