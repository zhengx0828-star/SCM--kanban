# 口径定义（DOH 四档）

> 关联：`01-设计方案.md`
> **本文档是唯一权威口径**，后端 `_doh_bucket_of()`、前端 `INV_DOH_BUCKET_META`、规则页 SOP 三处必须与此一致。

---

## 1. DOH 定义（沿用现有，不改）

```
DOH（Days On Hand，动态库存天数）= 当日期末库存 ÷ 窗口日均需求
```

- 取值来源：`plan.days[0].doh`（今日）与 `plan.days[0].doh_capped`。
- `doh_capped = true` 表示 30 天窗口内库存未耗尽，`doh` 在输出时被钳到 30。**判定时按 30 处理**（即 `DOH ≥ LT` 一律充足，除非 LT > 30）。
- 日均需求 = 现有 `plan.avg_daily`（窗口日均），**不另算**。

---

## 2. 四档判定（严格优先级）

```python
import INV_URGENT_DOH_THRESHOLD as URGENT_ABS   # = 3（绝对阈值，天）

def _doh_bucket_of(out, lead_time: int) -> str:
    # 0. 需求不可用三档优先，绝不入正常档
    if out.bom_zero:
        return "unknown"
    if len(out.hist) == 0 and len(out.fcast) == 0:
        return "unknown"
    if out.demand_blank and not out.bom_zero:
        return "unknown"

    d0 = out.days[0]
    doh = 30.0 if d0.doh_capped else d0.doh
    safe = out.safe_days
    lt = lead_time

    # 1. 耗尽
    if doh <= 0 or d0.status == "stockout":
        return "stockout"
    # 2. 紧急：跌破安全线，或 DOH 低于绝对阈值（两者并行，谁先命中算谁）
    if doh < safe or doh < URGENT_ABS:
        return "urgent"
    # 3. 偏低（左闭右开）
    if doh < lt:
        return "low"
    # 4. 充足
    return "ok"
```

### 为什么需要绝对阈值（`DOH < 3 天` 强制紧急）

安全天数 = `Z × COV × √LT`。当**需求完全平稳**（每月需求量一致）时 `标准差 = 0` → `COV = 0` → **安全天数 = 0**。
此时判据 `doh < safe` 退化为 `doh < 0`，恒为假 —— 一行 DOH 只剩 **1 天** 的物料会被宽容地判成「③偏低」，
而它离「④充足」只差一档。业务上这恰恰是最该被盯住的行。

实测复现（种子数据）：

| 物料 | 基地 | DOH | 安全天数 | LT | 修正前 | 修正后 |
|---|---|---|---|---|---|---|
| 主控芯片 MCU-64 | 宁波 | 1.0 | 0.00 | 7 | 偏低 ❌ | **紧急** ✅ |
| 主控芯片 MCU-64 备选 | 青岛 | 6.4 | 0.00 | 7 | 偏低 | 偏低 |
| 多源结构胶 | 苏州 | 6.5 | 0.00 | 7 | 偏低 | 偏低 |
| 主控芯片 MCU-64 | 重庆 | 6.7 | 0.32 | 30 | 偏低 | 偏低 |

故叠加**绝对阈值兜底**：`DOH < 3 天一律紧急`，不依赖安全天数是否可算。
两套口径并行（`doh < safe` **或** `doh < 3`），不互相替代。

### 边界表（必须逐条对齐）

| 情形 | DOH | 安全天数 | LT | 判定 | 理由 |
|---|---|---|---|---|---|
| 已断货 | 0 | 5 | 7 | `stockout` | DOH≤0 |
| **安全天数=0，DOH 极低** | **1.0** | **0** | **7** | **`urgent`** | **绝对阈值 DOH<3 命中** |
| **安全天数=0，DOH 略高** | **6.4** | **0** | **7** | **`low`** | **未破绝对阈值，安全线也失效 → 按 LT 判** |
| 边界 ②/③ | 5.0 | 5 | 7 | `low` | `doh < safe` 不含等号，且 5 ≥ 3 |
| 边界 ③/④ | 7.0 | 5 | 7 | `ok` | `doh < lt` 不含等号 |
| 绝对阈值 ③/② | 3.0 | 1 | 10 | `low` | `doh < 3` 不含等号 |
| 安全天数 > LT | 6 | 10 | 5 | `urgent` | ②优先于③ |
| 安全天数 > 30 | 30(capped) | 45 | 7 | `urgent` | capped 按 30，仍 < 45 |
| LT > 30 | 30(capped) | 5 | 45 | `low` | capped 按 30，30 < 45 |
| BOM = 0 | 任意 | 任意 | 任意 | `unknown` | 需求被乘成 0，无意义 |
| 无序列 | 任意 | 任意 | 任意 | `unknown` | 数据缺失 |
| 需求为 0 | 30+ | 5 | 7 | `unknown` | 有序列但日均≈0 |

> **`doh_capped` 严禁当作"充足"判据**。capped 只说明"30 天内耗不完"，若 LT=45，DOH 30 天仍然不够走完采购周期 → `low`。这是旧漏斗最易出错的地方（旧代码用 `not d0.doh_capped and d0.doh < lt` 短路，会让 LT>30 的行永不亮灯）。
>
> **绝对阈值调参位置**：`backend/app/schemas.py` 的 `INV_URGENT_DOH_THRESHOLD`（当前 3 天）。改这里即可全站生效（四卡、列表、概览、导出共用同一入口）。

## 3. 与旧「下单时机漏斗」的关系

| | DOH 四档（新，主） | 下单时机（旧，降级为细条） |
|---|---|---|
| 参数 | `days[0].doh`、`safe_days`、`lead_time_days` | `days[i].ending ≤ plan.rop` 首次命中日 |
| 维度 | 库存健康度 | 补货动作时机 |
| 分档 | 耗尽/<安全/<LT/≥LT | 今日/D2-7/D8-14/D15-30 |
| 是 DOH 的下游 | — | ✅ ROP = (LT + 安全天数) × 日均，是 DOH 的推论 |

两者**互斥过滤**（前端同时只生效一个）。

## 4. 「无法评估」灰卡的口径

- 计数 = `doh_buckets.unknown`。
- 卡片 hint 必须**分列三种成因的计数**，例如：`缺需求 1 · BOM为0 1 · 需求为0 0`。
- 点击灰卡 = 过滤出所有 `unknown` 行，方便集中补录。
- **视觉上必须比"充足"绿卡弱**（灰底），避免用户误以为它是好状态。

## 5. 数据不可用的三档判定（沿用现有，不改）

现有前端逻辑（`PlanBlock` 内）已正确实现，**原样搬入抽屉与四卡判定**，不得重写：

```
noDemandData = hist.length === 0 && fcast.length === 0      // ① 缺需求数据
bomZero      = plan.bom_zero                                 // ② BOM 系数显式 0
blankDemand  = plan.demand_blank && !bomZero && !noDemandData // ③ 有序列但窗口日均≈0
```

**硬约束**：`has_series = bool(hist or fcast)`，**勿写 `or source == MASTER`**，否则"无序列"会被误判成"需求为 0"。
